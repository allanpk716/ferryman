日期:2026-09-18 · 状态:rev1(消化 round 0 评审 10 条必改 + 1 条实验排除;原稿 20260918-subagent-token-audit-consensus.md 不动)
术语:遵守仓库 CONTEXT.md「记账」一节(子代理转录 / 四列口径 / 会话总账 / 对账)。

## 1. 问题陈述

用户在主会话里讨论方案后,执行阶段会拆出若干子代理(subagent)并行干活。用户想知道:主会话自身用了多少 token、每个子代理各耗多少、一共开了几次子代理。经调查,这些数据**今天没有任何工具在记录**,但原始数据全部躺在磁盘上,纯增量工作即可取得。

## 2. 已验证事实底座(全部本机实测,2026-09-18;含 round 0 评审查证结果)

### 2.1 数据源与磁盘布局(Claude Code)

布局写死(文件与目录**并存**):

- 主转录:`~/.claude/projects/<项目目录>/<会话id>.jsonl`(一个会话一个文件);
- 子代理目录:同名目录 `~/.claude/projects/<项目目录>/<会话id>/`(该会话开过子代理时存在),其下 `subagents/` 里每个子代理一对文件:
  - `agent-<agentId>.jsonl`:完整对话记录,每条 assistant 行带官方 usage 四列(input_tokens / output_tokens / cache_creation_input_tokens / cache_read_input_tokens)与 model 字段;
  - `agent-<agentId>.meta.json`:agentType、description、toolUseId(关联父转录里的 Agent/Task 调用)、spawnDepth(嵌套深度)、model(**请求别名,非实际服务模型**)、requestShape。

本机格式普查:284 个顶层会话文件中 0 个老式内嵌 sidechain(`isSidechain:true` 行),94 个会话有 `subagents/` 目录——只需支持一种格式。嵌套子代理真实存在:1430 个 spawnDepth=1、43 个 spawnDepth=2。

### 2.2 转录行结构:必须按 message.id 去重(round 0 查实 #1)

一个 API 响应(一个 message.id)在 jsonl 里拆成**多行**(每个内容块一行:thinking / text / tool_use 各一行):

- 带 `stop_reason` 的行携带该响应**完整 usage**;同一 message.id 的多行携带**同一份 usage 拷贝**;
- 流式前置行的 usage 是 0/null 占位,不是真消耗。

实测(抽样子代理文件):48 条 assistant 行仅 15 个唯一 message.id;逐行加总 in+out=159,265,**按 message.id 去重取非空 usage=74,016**,与 CLI 自报 75,395 对上 98%。全量扫描:1735 文件 0 重复 uuid,但 **1698 文件存在重复 message.id(多出 87,413 行)**;主会话文件同构(166 行/55 响应=3.02 倍)。

**记账规则(定死)**:每个文件内,assistant 行按 message.id 分组,每组取任一非空 usage,四列分别加总。不去重会虚增 2~3 倍。

### 2.3 嵌套不双重计账(round 0 实验 #11 排除)

取本机 43 个 spawnDepth=2 样本中的 12 个,按 meta.toolUseId 定位父代理文件,对比父子消息 uuid 集合:**12/12 零重叠**——depth-2 消息只在自己的文件里,不出现在 depth-1 父文件。Σ 全部 `agent-*.jsonl` 不双重计账。注意:父代理会吞子代理**结果文本**进后续上下文(计入父的后续 input/cache_read),这是回传耦合(§4.2),不是 usage 重复。

### 2.4 对账口径(round 0 查实 #1/#3/#7)

- 原"对账发现"(自报 75,395 vs 加总对不上)的谜底已解:**对不上是因为逐行加总虚增**;去重后与自报对上 98%,残差 ~2%(1,379 token)未解释,报告如实标注。
- CLI 自报数的性质:任务完成通知里的瞬态字段,**磁盘无持久化留存**(grep 全 ~/.claude 仅会话正文文本命中)→ 历史会话无法回溯对账。

### 2.5 Codex 侧(范围外,事实留档)

Codex rollout 有逐响应 `token_usage_record`(thread_id / turn_id / root_turn_id / usage),但本机全部 354 个 rollout 中零个子代理线程——没有真实数据样本,无从验证,本轮不做。

### 2.6 守护进程现状(被测系统的既有实现)

- 守望器显式跳过 `subagents/` 目录(既有决策:子代理转录不是独立会话,不摆渡)——子代理 token 数据至今一个字都没进过系统。
- 台账纯内存、无 token 字段、重启即丢;子代理只有瞬时运行计数(归零即删),无累计次数。
- 既有 CC 解析器只读输入三项,不读 output_tokens、不读 model;逐行读 usage(受 §2.2 拆行结构影响,任何"逐行求和"式统计都会虚增;现有 peak_ctx 取 max 不受影响)。
- 无价格表、无成本计算;子代理钩子链路已通但端点丢弃 agent_id 与转录路径;无任何按会话查询 token 的接口。
- 有利资产:防御式 usage 读取器可复用;`Facts.total_input_tokens` 字段已存在无人消费。

## 4. 实验设计(e0c)

### 4.1 要回答的四组问题

1. **核心三问(原始需求)**:逐会话出明细账——主会话自身 token、每个子代理各耗 token(self 口径,另附 subtree 见 4.2)、子代理开启次数。
2. **占比与分布(定型依据)**:子代理消耗占会话总账的比例;按子代理类型(Explore / general-purpose / …)、嵌套深度(spawnDepth)、实际服务模型(行级)的分布。**固定注明回传耦合**:子代理结果回传主会话后,其文本以 input/cache_read 形式再计入主会话后续请求(实测案例:回传后主会话 in 237→1259),"子代理占比"因此结构性偏低、主会话偏高——占比只作方向参考,不构成"子代理不重要"的证据。
3. **对账自校验(拒绝玄学)**:采集方法定死——CLI 自报数只在**实验运行期间实时抓取**(任务完成通知的瞬态字段),配对键 = agentId,与去重四列加总逐个对比;目标样本量 ≥10(实验期间新完成的子代理不足则如实报告实际样本数);残差逐个列出,不解释的不硬解释。
4. **长尾坑清单(防御式边界)**:中断的(最后一条不是 assistant 收尾/无 stop=end_turn)、空文件、在跑中(扫描时写入未停稳)、meta 与转录不成对(规则见 4.2)等异常样本的分布与占比;主文件 Task 调用数 vs meta 数 vs jsonl 数的三值交叉差。

### 4.2 口径与聚合(全部定死,不留"待定")

- **记账唯一事实源** = 文件内官方四列;任何自报汇总数仅作对账参照。
- **聚合规则** = §2.2:按 message.id 去重取非空 usage,四列分别加总;主会话、子代理、总账同一条规则。
- **主会话消耗** = 主 jsonl 去重加总(主文件只含主循环请求)。
- **子代理消耗(双口径)**:每子代理记 **self tokens**(自身文件去重加总)与 **subtree tokens**(self + 全部后代);账单主行用 self,subtree 列附加。
- **开启次数(双口径)**:**direct spawn count**(该会话 spawnDepth=1 的子代理数,对应用户"主会话开了几次")与 **total spawn count**(全部深度);计数基准 = 子代理 jsonl 文件数;meta 数与主文件 Task 调用数作交叉校验,差值进长尾清单。
- **模型分组** = 按每条 usage 所在响应的**行级 message.model** 聚合(本机走中转:meta.model 是请求别名,1265/1450 与实际服务模型不一致;7 个文件内行级模型多于一个,正是中途换模型/fallback 的证据);meta.model 仅作元数据与一致性校验列。
- **meta/转录不成对默认规则**:有 jsonl 无 meta → token 照入总账,agentType 标 `未知`,model 取行级;有 meta 无 jsonl → 计数 +1、token 记 0,标 `无转录`;两类都进长尾清单,不剔除、不猜测。
- **快照一致性**:每个被读文件记录(扫描时刻, 文件大小, 内容哈希);会话级记录扫描窗口起止;活跃会话(扫描时 mtime 距扫描 < 5 分钟)整场标 `在跑(非终值)`,报表中该行不进终值口径的汇总;稳定判据沿用稳定快照思路(同偏移同哈希两次读)——实验级允许 mtime+size 粗判,但扫描时刻戳必须落盘。
- **族系合计行**:复用台账既有 lineage 识别规则出合计行,同时输出识别依据(链上会话 id 列表);合计行标注 `识别未验证`。

### 4.3 交付物

- `ferryman/e0c.py`:可复用测量套件——解析层纯函数(输入文件路径,输出结构化账目),实验脚本只做 IO 与聚合;勿一次性脚本。
- `reports/e0c-cc-subagent-tokens.md`:中文实验报告,四组问题各一节 + 定型建议(附判据,不附决定——决定权在用户)。

### 4.4 明确不做(本轮)

实时监控、Codex、钱换算、守望器/台账/钩子的任何改动——全部留待实验数据出来后的定型决策。

## 5. 风险与开放点(留给开发)

- 族系识别规则复用台账既有实现,识别准确率未预验证——开发时核实,合计行按 4.2 标注。
- 对账残差 ~2% 未解释——报告如实列出,不硬解释。
- 实验期间在跑会话的判定窗口(5 分钟)是经验值,长尾清单会给出实际分布,定型时再校。
- 子代理 jsonl 半行写入的防御式读取,复用既有读取器先例。
