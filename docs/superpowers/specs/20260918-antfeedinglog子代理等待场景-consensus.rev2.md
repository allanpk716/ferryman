# 子代理等待场景：守护系统行为评估与缺口修复建议（rev2）

- **日期**：2026-09-18（rev2：吸收第二轮评审 11 条精度问题——上界分道如实、A7 重写、文案确定性出路、删冗余规格、前提声明；rev1 曾修首轮 11 条）
- **性质**：场景评估修订稿（对话固化，供评审）
- **历史背景（中性陈述）**：本稿 rev0 有评审指出规格含混/无验收/断言无引用，rev1 修订后又有评审指出两处断言过度确定与验收规格矛盾，均已在本版解决。

## 场景与背景

某本机项目进入开发执行阶段，工作模式 = 主会话派发子代理任务后等待返回。本机常驻一套会话守护系统（下称"守护"）：主会话闲置 25 分钟自动生成交接文档，35 分钟后拦截新输入并引导 /clear 开新会话（自动注入交接+用户被拦原话）；另有一项"心跳保活"机制已设计定案但未实装、未获授权（授权需过数据门槛+保真实验+明确放行三关）。

缓存经济：服务商缓存 TTL 实测 600 秒；前缀约 150k token 的会话缓存死后恢复需全款重付约 103 积分/次。

## 实测数据（2026-09-18 上午，该项目真实账本）

- 2 小时 69 次请求，上下文前缀 p50=150k、max=240k；总花费≈2245 积分；全款重付（缓存死）0 起；拦截/警告/摆渡均为 0（零干扰）。
- 该项目会话尚无子代理派发记录（评估的是即将进入的工作模式）。
- 守护历史全部 52 个等待窗口：p50=36s、max=155s，全部小于 TTL 600s。**前提声明**：①这 52 窗全部由子代理事件开启（ferryman/server.py:354-360），但**无一超过 8 分钟，不含长任务样本**——对"即将进入的 10~40 分钟级 implementer 等待"无代表性，缓解表述仅适用于已观测模式；②window 流水 project 字段当前为空（记账时 cwd 未富化），按项目归因暂不可行，属已知数据缺口。

## 评估结论（时间轴）

- 等待 0~10 分钟（含全部已观测窗口）：缓存存活，零损失，守护全程安静。
- 等待 >10 分钟：缓存死，无任何机制保护（心跳未实装）——主会话恢复时 150k 全款重付≈103 积分/次。
- 闲置 25 分钟：摆渡检查发现子代理在飞→正确推迟（证据见断言表）。
- 等待 35 分钟+：缺口 A 爆雷区。

## 缺口 A（建议现在修）

闸门路径没有"子代理在飞/悬空 tool_use"检查（摆渡路径有），两处不一致：

1. 子代理任务跑超 35 分钟期间，用户在主会话输入→先警告、再拦截，拦截文案称"交接仍在生成"（实际摆渡被推迟、并无生成），用户按文案 /clear 会终止正在跑任务的会话。
2. 闸门警告分支（server.py:201-202）还会在子代理在飞时触发一次 mid-wait 摆渡（daemon 侧已推迟，闸门侧漏检）。

该行为与已裁决的三泳道表（机器等机器归心跳、人不在场才归摆渡/闸门）矛盾。

### 修复规格（精确版 · rev2）

**入口豁免（唯一改动点）**：

```
闸门入口处（bypass 判定之后、警告/拦截判定之前）：
若 ledger.subagent_active(agent, session_id) 为真
   或 has_dangling_tool_use(该会话 jsonl 路径) 为真：
    → 本次提交放行（decision=allow），不警告、不拦截、不入队摆渡、不动 pending（不清、不置、不 bump）
    → additional_context 附一句"[Ferryman] 子代理仍在运行，已放行本次输入"
```

要点（rev2 修订处加 ★）：

- **两道检查 OR 关系，互为兜底**。★真正需要悬空道兜底的场景是：①计数泄漏期已过（1h 无事件清零）但 tool_result 仍缺——计数=0 且悬空=真；②守护进程重启导致内存计数丢失——悬空道是唯一防线。（rev1 曾举"Stop 丢失且未过泄漏期"为例，时序有误：该期间计数停在 1，计数道已放行，轮不到悬空道。）
- ★**两道豁免的上界分开如实声明**：
  - 计数道：内存计数最坏误活 **1 小时**（ledger.py:28 泄漏保护，时间上界）。
  - 悬空道：**无时间上界，有内容量上界**——检测只看 jsonl 尾部 256KB 滑窗（transcripts.py:73 `tail_bytes`），悬空事件被约 256KB 后续内容顶出窗口即失效（活会话持续使用必然成长→自然恢复拦截；已实验证实：悬空尾部=True / tool_result 落盘=False / 悬空后追加 290KB 内容=False）。会话闲置不成长期间悬空道持续豁免，但闸门只在用户提交时触发——提交本身即写入、即开始把悬空调出窗口。方向与守护"宁可不拦"的保守取向一致。
  - 最坏组合（计数泄漏 + 悬空且会话低速成长）下豁免期可超过 1 小时，按内容量收敛；此为本修复的真实行为偏差包络，不再以"1h"一言蔽之。
- **悬空检测的生命周期**：对尾部 256KB 的纯函数，每次闸门调用现算，无持久状态、无清理规则需要；tool_result 落盘即自愈。★宿主支持 resume 续同一 transcript：崩溃留下的悬空在会话恢复使用后会随内容成长被尾窗淘汰，不构成永久豁免（见上条）。
- ★**与既有 pending 的交互**：豁免不清、不置、不 bump pending——豁免只表达"此刻机器在跑"，pending 表达"该会话曾进入应交接状态"，两者独立；pending 生命周期照旧（新闲置周期规则，server.py:148-151）。验收 A8 覆盖组合场景。
- ★**不新增分支 7 入队检查**（rev1 曾要求"入队点同款前置检查"，第二轮评审确认同请求内不可达——入口豁免生效时流程到不了分支 7；enqueue 的另一调用方 daemon tick 自带同款检查 daemon.py:123-125）。本修复只改闸门入口一处。

### 竞态分析（★前提声明版）

**前提**：单用户本机场景，主会话的派活由该会话自身的用户输入触发（无外部自动化触发源）；存在其他触发源（排队输入、连续输入、外部自动化）时下述"不可达"不成立。

闸门与子代理事件在 ThreadingHTTPServer 下并发（server.py:21,423），共享 `_windows`。逐项核查：
- 窗口双关/迟关：`_close_window` 以 `pop` 幂等（server.py:270），重复触发无副作用。
- 检查后子代理恰结束：闸门放行了一条本可拦截的输入——该输入本身就是主会话恢复信号，窗口以 `close_reason=prompt` 正常闭合（server.py:123-124），语义正确。
- ★检查后子代理恰开始：在上述前提下（派活由本次放行的输入触发）**基本不可达**——派活晚于本次闸门调用；例外：前一条输入已放行但其 SubagentStart 事件尚未入账时，下一条输入的检查可能读到计数=0——后果至多一次多余警告/入队，由 daemon 3s tick 重查与 `valid_handoff` 的 covers_until+60s 容差二次校验（store.py:107）吸收，有界。
- 结论：不引入新锁；现有幂等+二次校验+短周期重查覆盖**已识别的**竞态面（不声称"全部"竞态面）。

### 放行后输入语义（诚实声明 + 兜底设计）

用户在子代理运行期间提交的输入，在宿主 CLI 里是**排队到当前回合结束再处理**还是**立即打断**，**未经实验验证**（验证需人工在交互式会话中打字，自动流程做不了，见验收 A6）。本修复的设计对此**不敏感**：排队则回合结束后正常处理（last_write 已更新，下轮闸门自然走正常路径）；打断则用户已显式接管，更不该拦。文案义务：放行提示不承诺输入的生效时机。

## 缺口 B（拆半处理，rev2 维持）

"强续"逃生前缀是单次放行（当时裁决；★本轮评审有一条优先级意见建议行为级提前修，用户裁决维持缓修），放行后不清警告态→用户强续继续工作后，后续提交被连续拦截且原文案不实，第 4 次才降级放行（server.py:32,187；★强续本身不计入拦截计数——server.py:126-133）。

**拆半**：
1. **文案级缓解（随缺口 A 一起修，不动裁决）**：分支 6 文案改为如实+**确定性出路**（对齐用户对拦截文案的明确要求；rev1 版"第 4 次起自动放行"因剩余拦截次数对用户不可预测而被第二轮评审否决）："此会话闲置超时被拦过，交接不覆盖你之后的新内容。继续干活：**每次以「强续」开头发消息（每一条都会放行，无需数次数）**；或 /clear 换会话（自动注入交接与你的原话）。"
2. **行为级修复（清 pending，维持等实际咬到再裁决）**：在检测到"会话已恢复活跃"（last_write 晚于 pending 置位且当前 idle < summarize 阈值）时清警告态——需修订"单次放行"裁决适用范围，按用户裁决维持缓修。

## 建议（rev2）

1. 现在修缺口 A（按上方精确规格）+ 缺口 B 文案级缓解（不动裁决）——对齐已裁决政策，非新政策。
2. 缺口 B 行为级修复等实际咬到再裁决（用户 2026-09-18 裁决维持缓修）。
3. 心跳授权数据门槛照常积累（52 窗全为短窗，无长任务样本——见前提声明）。
