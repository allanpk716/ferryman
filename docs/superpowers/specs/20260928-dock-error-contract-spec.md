# 渡口错误契约与热修（spec）

> 来源：2026-09-28 会话共识（三轮设计拷问 14 问全落定）＋两轮异构评审收敛（codex/kimi，一轮自动修订）。

## Problem Statement

2026-09-28 早晨，Claude Code 两次报 "Connection lost mid-response"，经查证根因是守护进程重启时渡口用「立即断监听＋断所有在途连接」的方式关停，把在途 SSE 流掐断——CC 收到的是它无法正确响应的裸断连。同时排查确认：渡口对上游非 200 响应已是零改写透传（不劣于参考实现 cc-switch），但渡口自身产生的错误（拨号失败回空体 502、上游 200 后挂死无超时、关停掐流无解释）不符合任何 CC 认识的标准形状，且截断的流在账本上零痕迹、关停来源无日志。需要一份成文的错误契约并实施五件热修，使「渡口永不让 CC 看到无解释的断连」。

## Solution（用户视角）

守护重启或换装时，在途的长回复不再被无声掐断：关停先等在途请求跑完（上限 180 秒），到期才收尾且收尾带标准错误事件。上游连不通时，CC 收到带原因与退避提示的标准错误并自动重试。上游回 200 后长时间不吐数据时，60 秒内 CC 得到可重试错误而不是永远挂起。上游自己的错误（429/5xx 等）原样到达 CC，其官方重试机制照常工作。账本记录被截断的流；守护关停时记录是谁发起的关停。

## User Stories

1. 作为 CC 用户，我想要守护重启/换装时在途回复不被无声掐断，以便长回复不在中途丢失。
2. 作为 CC 用户，我想要上游连不通时收到带原因的标准错误与退避提示，以便 CC 自动重试而非界面显示无名错误。
3. 作为 CC 用户，我想要上游 200 后挂死时在 60 秒内得到可重试错误，以便请求不会挂到天荒地老。
4. 作为 CC 用户，我想要上游错误（429/401/403/500/502/503/529 等）状态码、错误体、响应头（含 retry-after）原样到达，以便 CC 的官方重试/退避机制照常工作。
5. 作为运维者，我想要账本记录被截断的流（truncated 标记），以便事故排查时知道发生过截断。
6. 作为运维者，我想要守护优雅关停时记录关停来源（/shutdown 端点、托盘退出、Ctrl+C 信号），以便「谁重启的」不再成悬案。
7. 作为本仓开发者，我想要错误契约成文（CONTEXT.md 术语＋ADR-0017），以便未来改动不破坏 CC 的错误响应机制。

## Implementation Decisions

### 契约（成文为 CONTEXT.md 两条术语 + ADR-0017）

- **响应保真（response fidelity）**：上游非 200 的状态码、响应体、响应头零改写透传；响应侧出现任何改写要么是缺陷要么过 ADR。管辖范围＝上游非 200 响应的转发；渡口自产的流内终止不在此列。
- **渡口自产错误（dock-originated error）**：渡口自身产生的错误一律输出 CC 已认识的标准形状，永不裸断连；按流状态分流投递：
  - 首字节未写出（响应头尚未发给 CC）→ HTTP 状态（502/504）＋ Anthropic 错误体（`{"type":"error","error":{"type":"api_error","message":...}}`）＋ `Retry-After`；
  - 流已建立（200 已写、SSE 进行中）→ 先合成一个 Anthropic 流内错误事件（SSE `event: error`）再断连。
- **声明式残余边界**（不可消除、须成文）：
  - 上游已建立流后自己断连/干净 EOF 截断 → 连接断（不抢救，与参考实现一致）＋账本 truncated 记账；
  - 非流式请求在排水到期时 200 已写出、body 未传完 → 无合法错误投递通道，收尾＝断连＋尽力记账（round1 评审新增边界）；
  - 关停来源日志只覆盖自愿退出路径（/shutdown/托盘/信号），外部强杀与崩溃无进程内日志机会。
- 维持「整流 no-op」旧决定：不移植参考实现的换家/熔断（本项目换上游纯手动）。

### 优雅排水（热修第 1 件）

- 渡口 Server 增加 `Shutdown(ctx)`：先停收新连接，等在途请求自然结束；排水上限可配置（`[dock]` 节新键，默认 180 秒），到期对流已建立的在途请求逐个合成 Anthropic 流内错误事件后硬收（`Close`），首字节未写出的请求直接回 504＋错误体。
- daemon 关停路径由「立即 Close」改为「Shutdown（带上限）→ 到期 Close」。

### 拨号失败错误体（热修第 2 件）

- 反向代理补错误处理器：上游连不通等出站错误（此时客户端首字节未写出）→ 回 502（或语义更准的状态）＋ Anthropic 错误体（含一句人话原因）＋ `Retry-After` 短值（约 5 秒）。替换 Go 标准库默认的空体 502。

### 首包闸门（热修第 3 件）

- 仅流式请求（/v1/messages POST 且请求体 `stream:true`）：上游响应头到达后不立即转发给客户端，等到首个流字节到达才放行（首字节随后的体一起续传）；静默超 60 秒判失败 → 走「首字节未写出」路径回 504＋错误体＋`Retry-After`。
- 非流式请求不闸（慢生成是合法行为，避免误杀）。上游响应头等待沿用既有 50 分钟上限，不动。

### 干净 EOF 观测（热修第 4 件）

- 既有 SSE usage 扫描器顺带记录 `message_stop` 是否出现；流 EOF 时已见过至少一个 SSE 事件但未见 `message_stop` → dock 科目流水行加 `truncated` 标记并记一行日志。纯观测：不改转发字节、不改客户端行为。非 SSE 响应（无事件可见）不标记。

### 关停来源落日志（热修第 5 件）

- 三个自愿退出源（`/shutdown` 端点、托盘退出、Ctrl+C/中断信号）在取消主 context 前各记一行日志（来源＋时间）。外部强杀/崩溃不在覆盖内（声明式残余）。

### 接口与兼容

- 记账：dock 科目流水行新增 `truncated` 字段仅出现于截断行（缺省不写），旧流水不受影响；读侧（report/面板）对该字段宽容忽略。
- 配置：`[dock]` 节新增排水上限键（缺省 180 秒），解析层单源既有纪律不变。
- 快照/改写五件/心跳重放路径零触碰：本 spec 不改任何请求侧行为。

## Testing Decisions

- 只测外部行为（渡口对客户端的可见行为与账本行），不测内部结构；沿用 dock 包既有 httptest 桩风格（上游用 httptest.Server 桩）。
- 上游透传组：桩回 429/401/403/500/502/503/529（带 retry-after 头与 JSON 体）→ 断言客户端实收状态码/体/头三者一致。
- 拨号失败：上游地址不可达 → 断言 502＋Anthropic 错误体＋Retry-After 存在。
- 首包闸门：桩回 200 头后不吐体（注入短超时）→ 断言 60 秒语义路径回 504＋错误体；正常流 → 断言首字节不迟于上游首字节到达（无额外缓冲延迟）。非流式慢响应不触发闸门。
- 优雅排水：在途流进行中触发 Shutdown（注入短排水上限）→ 断言在途流跑完；到期未完 → 断言客户端收到 `event: error` 流内事件后连接关闭。
- 截断记账：桩发若干 SSE 事件后直接 EOF（无 message_stop）→ 断言流水行带 truncated；完整流（有 message_stop）不带。
- 关停来源：分别经三个源触发关停 → 断言日志各有一行来源。
- 人工验收：`internal/dock/SMOKE.md` 13 行清单（上游透传 8 行＋渡口自产 5 行，每行三查：怎么触发｜渡口回什么｜CC 预期做什么），作为发布前行为面验证脚本（与本仓 widget SMOKE.md 同纪律）。
