# 子代理等待场景：守护系统行为评估与缺口修复建议（rev1）

- **日期**：2026-09-18（rev1：吸收首轮评审 11 条查实问题——规格补全、断言补引用、缺口 B 拆半、新增验收标准）
- **性质**：场景评估修订稿（对话固化，供评审）
- **历史背景（中性陈述）**：本稿 rev0 曾有评审指出修复规格含混、无验收标准、断言无引用、缺口 B 缓修理由不全，均已在本版解决。

## 场景与背景

某本机项目进入开发执行阶段，工作模式 = 主会话派发子代理任务后等待返回。本机常驻一套会话守护系统（下称"守护"）：主会话闲置 25 分钟自动生成交接文档，35 分钟后拦截新输入并引导 /clear 开新会话（自动注入交接+用户被拦原话）；另有一项"心跳保活"机制已设计定案但未实装、未获授权（授权需过数据门槛+保真实验+明确放行三关）。

缓存经济：服务商缓存 TTL 实测 600 秒；前缀约 150k token 的会话缓存死后恢复需全款重付约 103 积分/次。

## 实测数据（2026-09-18 上午，该项目真实账本）

- 2 小时 69 次请求，上下文前缀 p50=150k、max=240k；总花费≈2245 积分；全款重付（缓存死）0 起；拦截/警告/摆渡均为 0（零干扰）。
- 该项目会话尚无子代理派发记录（评估的是即将进入的工作模式）。
- 守护历史全部 52 个等待窗口：p50=36s、max=155s，全部小于 TTL 600s。**前提声明**：①这 52 窗全部由子代理事件开启（窗口定义即如此，ferryman/server.py:354-360），但**无一超过 8 分钟，不含长任务样本**——对"即将进入的 10~40 分钟级 implementer 等待"无代表性，缓解表述仅适用于已观测模式；②window 流水的 project 字段当前为空（记账时 cwd 未富化），按项目归因暂不可行，属已知数据缺口。

## 评估结论（时间轴）

- 等待 0~10 分钟（含全部已观测窗口）：缓存存活，零损失，守护全程安静。
- 等待 >10 分钟：缓存死，无任何机制保护（心跳未实装）——主会话恢复时 150k 全款重付≈103 积分/次。
- 闲置 25 分钟：摆渡检查发现子代理在飞→正确推迟（证据见下）。
- 等待 35 分钟+：缺口 A 爆雷区。

## 缺口 A（建议现在修）

闸门路径没有"子代理在飞/悬空 tool_use"检查（摆渡路径有），两处不一致：

1. 子代理任务跑超 35 分钟期间，用户在主会话输入→先警告、再拦截，拦截文案称"交接仍在生成"（实际摆渡被推迟、并无生成），用户按文案 /clear 会终止正在跑任务的会话。
2. 闸门警告分支（server.py:201-202）还会在子代理在飞时触发一次 mid-wait 摆渡（daemon 侧已推迟，闸门侧漏检）。

该行为与已裁决的三泳道表（机器等机器归心跳、人不在场才归摆渡/闸门）矛盾。

### 修复规格（精确版）

**放行/推迟条件（两道检查，与摆渡路径逐一对齐）**：

```
闸门入口处（bypass 判定之后、警告/拦截判定之前）：
若 ledger.subagent_active(agent, session_id) 为真
   或 has_dangling_tool_use(该会话 jsonl 路径) 为真：
    → 本次提交放行（decision=allow），不置 pending、不警告、不拦截、不入队摆渡
    → additional_context 附一句"[Ferryman] 子代理仍在运行，已放行本次输入"
分支 7 的入队摆渡（enqueue_ferry）加同款前置检查：条件为真则不入队
```

要点：
- **两道检查缺一不可**：只补计数则"计数=0 但悬空 tool_use"（如 Stop 事件丢失且尚未过 1h 泄漏期）的会话仍会被误拦。计数是内存态、悬空是文件态，互为兜底。
- **悬空检测的生命周期**（无清理规则的负担）：它是对 jsonl 尾部的纯函数（transcripts.py:73-101），每次闸门调用现算，无持久状态；tool_result 落盘即自愈；会话崩溃留下的永久悬空属于死会话（不再有提交，闸门不会为其调用），天然不构成"长期误放行"。
- **泄漏上界**：内存计数最坏误活 1 小时（ledger.py:28 泄漏保护），期间该会话免拦——这是本修复引入的最大行为偏差，上界明确（1h），且与"宁可不拦"的守护保守方向一致。

### 竞态分析（为什么有界）

闸门与子代理事件在 ThreadingHTTPServer 下并发（server.py:21,423），共享 `_windows`。竞态后果经代码核查全部有界：
- 窗口双关/迟关：`_close_window` 以 `pop` 幂等（server.py:270），重复触发无副作用。
- 检查后子代理恰结束：闸门放行了一条本可拦截的输入——该输入本身就是主会话恢复信号，窗口以 `close_reason=prompt` 正常闭合（server.py:123-124），语义正确。
- 检查后子代理恰开始（用户输入触发的派活）：派活必然晚于本次闸门调用（输入还没放行就没有派活），时序上不可达。
- mid-wait 摆渡残race：daemon 侧 3s tick 重查（`poll_interval_s=3`），且交接可用性由 `valid_handoff` 的 covers_until+60s 容差二次校验把关（store.py:107），过期交接不会被用于拦截。
- 结论：不需要引入新锁；现有幂等+二次校验+短周期重查已覆盖全部竞态面。

### 放行后输入语义（诚实声明 + 兜底设计）

用户在子代理运行期间提交的输入，在宿主 CLI 里是**排队到当前回合结束再处理**还是**立即打断**，**未经实验验证**（验证需人工在交互式会话中打字，自动流程做不了，见验收标准 A6）。本修复的设计对此**不敏感**：无论哪种语义，闸门侧"放行+不动手"都是正确动作——排队则回合结束后正常处理（此时 last_write 已更新，下轮闸门自然走正常路径）；打断则用户已显式接管，更不该拦。唯一的文档义务是把这一点写进拦截/放行文案，不承诺输入的生效时机。

## 缺口 B（拆半处理）

"强续"逃生前缀是单次放行（当时裁决），放行后不清警告态→用户强续继续工作后，接下来 3 次提交被连续拦截且文案不实（"交接仍在生成"，实际无生成——摆渡只在新闲置 25 分钟后才可能再触发），第 4 次才降级放行（server.py:32,187）。

**拆半**：
1. **文案级缓解（随缺口 A 一起修，不动裁决）**：分支 6 文案改为如实陈述+明确下一步动作（对齐用户对拦截文案的明确要求）："此会话闲置超时被拦过，交接不覆盖你强续后的新内容。继续干活：直接再发一次（第 4 次起自动放行）；或 /clear 换会话（自动注入交接与你的原话）。"——不实陈述消除，单次放行裁决保持原样。
2. **行为级修复（清 pending，仍等实际咬到再裁决）**：在检测到"会话已恢复活跃"（last_write 晚于 pending 置位且当前 idle < summarize 阈值）时清警告态——需推翻/修订"单次放行"裁决的适用范围，维持"等实际发生再修"的原建议。

## 建议（rev1）

1. 现在修缺口 A（按上方精确规格）+ 缺口 B 文案级缓解（不动裁决）——对齐已裁决政策，非新政策。
2. 缺口 B 行为级修复等实际咬到再裁决。
3. 心跳授权数据门槛照常积累（52 窗全为短窗，无长任务样本——见前提声明）。

## 验收标准（新增）

单元/集成测试（挂在既有 196 例套件上，tests/test_gate.py）：
- [ ] A1 子代理计数>0 时提交：放行、不置 pending、不警告、不入队摆渡、context 带放行说明
- [ ] A2 仅悬空 tool_use（计数=0）时提交：同上放行（两道检查缺一不可的直接验证）
- [ ] A3 两道检查皆无、闲置≥35min：原警告/拦截行为零回归（对照既有分支 5/6/7 测试不改动全绿）
- [ ] A4 分支 7 入队：子代理在飞或悬空时 enqueue_ferry 不被调用（spy 断言）
- [ ] A5 强续后再次提交：拦截文案为新如实文案，第 4 次仍自动降级放行（裁决不变）
- [ ] A6 人工验收（一次性，修复合入后做）：交互式会话派一个 ≥3 分钟子代理，期间向主会话输入一条消息，记录守护日志中闸门调动的时刻（立即 vs 回合末）与输入生效方式（排队 vs 打断）——补上本稿声明的未验证事实，结果记入设计文档
- [ ] A7 泄漏场景：模拟 Stop 丢失（计数停在 1），1 小时后（或调小泄漏常量）闸门恢复拦截能力

## 不可越权约束

- 心跳执行器：未授权不实装（三道门槛铁律）。
- 修复只动闸门决策与入队条件 + 分支 6 文案，不引入新机制、不加新锁。
