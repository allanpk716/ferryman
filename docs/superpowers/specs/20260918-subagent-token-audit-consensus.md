# 共识文档 · Claude Code 子代理 token 记账测量实验（e0c）

日期：2026-09-18 · 状态：两轮结构化问答已达成的共识，待评审
术语：遵守仓库 CONTEXT.md「记账」一节（子代理转录 / 四列口径 / 会话总账 / 对账）。

## 1. 问题陈述

用户在主会话里讨论方案后，执行阶段会拆出若干子代理（subagent）并行干活。用户想知道：主会话自身用了多少 token、每个子代理各耗多少、一共开了几次子代理。经调查，这些数据**今天没有任何工具在记录**，但原始数据全部躺在磁盘上，纯增量工作即可取得。

## 2. 已验证事实底座（全部本机实测，2026-09-18）

### 2.1 数据源（Claude Code）

- 每个会话目录 `~/.claude/projects/<项目>/<会话id>/subagents/` 下，每个子代理一对文件：
  - `agent-<agentId>.jsonl`：完整对话记录，每条 assistant 消息带官方 usage 四列（input_tokens / output_tokens / cache_creation_input_tokens / cache_read_input_tokens）与 model 字段；
  - `agent-<agentId>.meta.json`：agentType、description、toolUseId（关联主会话 Task 调用）、spawnDepth（嵌套深度）、model、requestShape。
- 主会话 jsonl 只记主循环自身的请求消耗；Task 工具的 toolUseResult 里**没有**任何 token 汇总。
- 因此：**会话总账 = 主转录四列加总 + Σ 各子代理转录四列加总**，必须自行计算。
- 子代理转录**没有显式完成标记**，文件以最后一条 assistant 消息收尾；"还在跑 vs 已结束"只能靠文件写入停稳推断（与摆渡的稳定快照同思路）。
- 本机格式普查：284 个顶层会话文件中 0 个老式内嵌 sidechain（`isSidechain:true` 行），94 个会话用 `subagents/` 独立目录格式——**只需支持一种格式**。
- 嵌套子代理真实存在：本机 1430 个 spawnDepth=1、43 个 spawnDepth=2。

### 2.2 对账发现（口径黑盒）

抽样对账：CLI 自报某子代理总消耗 75,395 tokens，而同一子代理落盘文件按四列加总为 in+out=159,265、含缓存全口径≈1.50M，**任何一种加总都与自报数对不上**。结论：自报数口径是黑盒，记账只能以文件四列为准；自报数仅作对账参照。

### 2.3 Codex 侧（范围外，事实留档）

Codex rollout 有逐响应 `token_usage_record`（thread_id / turn_id / root_turn_id / usage 四列），但本机全部 354 个 rollout 中**零个**出现子代理线程（无 multi-thread、无 turn≠root 记录）——没有真实数据样本，无从验证，本轮不做。

### 2.4 守护进程现状（被测系统的既有实现）

- 守望器**显式跳过** `subagents/` 目录（既有决策：子代理转录不是独立会话，不摆渡）——子代理 token 数据至今一个字都没进过系统。
- 台账纯内存、无 token 字段、重启即丢；子代理只有瞬时运行计数（归零即删），无累计次数。
- 既有 CC 解析器只读输入三项，不读 output_tokens、不读 model。
- 无价格表、无成本计算。
- 子代理生命周期钩子链路已端到端落地（钩子 → HTTP 端点 → 台账），但端点丢弃了 payload 里的 agent_id 与转录路径。
- 无任何"按会话查询 token 消耗"的命令或接口。
- 有利资产：防御式 usage 读取器可直接复用于子代理转录解析；`Facts.total_input_tokens` 字段已存在但无人消费。

## 4. 实验设计（e0c）

### 4.1 要回答的四组问题

1. **核心三问（原始需求）**：逐会话出明细账——主会话自身 token、每个子代理各耗 token、子代理开启次数。
2. **占比与分布（定型依据）**：子代理消耗占会话总账的比例；按子代理类型（Explore / general-purpose / …）与嵌套深度的分布；按模型的分组消耗。
3. **对账自校验（拒绝玄学）**：抽样把文件四列加总与 CLI 自报数交叉比对，量化自报口径偏差。
4. **长尾坑清单（防御式边界）**：中断的（没写完就死）、空文件、在跑中（写入未停稳）、meta 缺失等异常样本的分布与占比。

### 4.2 口径与聚合

- 记账唯一事实源 = 文件内官方四列；任何自报汇总数不作账目依据。
- 主会话消耗 = 主 jsonl 全部 assistant 行四列加总（主文件只含主循环，无污染）。
- 子代理消耗 = 各 `agent-*.jsonl` 四列加总，附 meta 信息（类型 / 深度 / 模型 / 描述）。
- 账单以单个 session 文件为最小单位；另附按族系（resume 链）聚合的合计行（族系识别复用台账既有 lineage 规则）。
- 在跑中的会话（含实验运行当时活跃的）不排除，标记"在跑"。

### 4.3 交付物

- `ferryman/e0c.py`：可复用测量套件（解析层为纯函数，实验脚本只做 IO 与聚合——勿一次性脚本）。
- `reports/e0c-cc-subagent-tokens.md`：中文实验报告，四组问题各一节 + 定型建议（附判据，不附决定——决定权在用户）。

### 4.4 明确不做（本轮）

实时监控、Codex、钱换算、守望器/台账/钩子的任何改动——全部留待实验数据出来后的定型决策。

## 5. 风险与开放点（留给评审与开发）

- 族系识别规则复用台账既有实现，其对 resume 链的识别准确率未在本实验预验证（开发时核实）。
- "在跑中"判定（写入停稳阈值）需要定义，实验里可先按文件 mtime 与最后时间戳粗判。
- 子代理 jsonl 半行写入（写入中途快照）的防御式读取,既有读取器已有先例,复用即可。
- meta.json 与 jsonl 不成对（一方缺失）的样本如何入账,实验里按长尾坑清单记录后定规则。
