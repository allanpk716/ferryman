# 渡口翻译车道对照表(W1a)——OpenAI responses 方言 ↔ Anthropic messages 方言

> **地位**:本表是票 03(渡口 responses 翻译车道)的唯一规格,评审先审表后审码;实现与表冲突 = 实现错。
> **术语**(spec v0.4.0):Anthropic 方言 = CC 说的 `/v1/messages` 线协议;responses 方言 = codex 说的 OpenAI `/responses` 线协议;翻译车道 = 渡口内把 responses 逐句转成 Anthropic 的新车道。
> **事实来源**:全部方言行为取自参考实现 cc-switch(farion1231/cc-switch,MIT,Tauri 2)源码快照 `.scratch/cc-switch-ref/`,版本 3.20.4,commit `846de29c13ac4d65f164db8c15dd5fd58e29f972`(2026-09-28)。文中出处一律相对 `.scratch/cc-switch-ref/src-tauri/src/proxy/`,记作 `文件:行`。参考实现没有、由本仓裁断的内容集中在第 6 节,正文以"**本仓决定**"标出。
> **阅读约定**:请求向 = codex(responses)→ 上游(Anthropic);响应向 = 上游(Anthropic SSE/JSON)→ codex(responses SSE/JSON)。"丢弃"指不进上游请求体/不出现在客户端响应,不是报错。

## 0. 车道定位与总流程

- 车道启用判定:客户端为 Codex 家(AppType::Codex/GrokBuild)**且**命中 responses 路径守卫 **且** 供应商声明 Anthropic 线协议。三者定义见第 4 节(`providers/codex.rs:198-207`、`providers/codex.rs:168-196`)。
- 请求向五步(参考实现 `forwarder.rs:1561-1616`):
  1. model 改写(第 5 节,`forwarder.rs:1248-1265`、`forwarder.rs:1563`);
  2. 供应商输出上限覆写 `max_output_tokens`(`forwarder.rs:1572-1579`);
  3. 翻译 responses→Anthropic(第 1 节,`providers/transform_codex_anthropic.rs:228-439`);
  4. 翻译后处理:`[1M]` 剥离 + context-1m beta 旗标(`forwarder.rs:1597-1603`)、可选 Claude Code 身份模拟(`forwarder.rs:1604-1606`)、cache_control 断点注入(`forwarder.rs:1607-1615`);
  5. 出站体定稿:剥 `_` 前缀私有字段 + 键序规范化(`forwarder.rs:1689`、`forwarder.rs:3737-3739`、`json_canonical.rs:6-21`)。
- 响应向三分支(`handlers.rs:1570-1646`):上游标 SSE(或缺显式 JSON Content-Type 且请求为流式)→ 流式转换;请求流式但上游回 JSON → 合成 SSE 事件序列;请求非流式 → 整体转 responses JSON。
- 响应提交前还有一道 2xx 错误信封校验(HTTP 200 但 body 是 Anthropic error 信封 → 按失败处理,可换上游;`forwarder.rs:2415-2418`、`forwarder.rs:2498-2526`、`forwarder.rs:3063-3077`)。

### 1.2 `input` 项 → messages 重嵌套(`convert_input_to_messages`,`providers/transform_codex_anthropic.rs:507-722`)

通用机制:同 role 相邻块合并进同一条 message(`push_block`,`providers/transform_codex_anthropic.rs:1122-1135`);tool_result 块永远排在所在 user 消息里任何 text/image 块之前(Anthropic 顺序要求,`push_tool_result_block`,`providers/transform_codex_anthropic.rs:1139-1158`);thinking 块插在 assistant 消息头部 thinking 块序列之后(`providers/transform_codex_anthropic.rs:1160-1179`)。

| input 项 | Anthropic 块 | 规则 | 出处 |
|---|---|---|---|
| `{type:"function_call", call_id, name, namespace?, arguments, status?}` | assistant `tool_use` | `call_id` 缺省回退 `id`;`arguments` 空串→`{}`、必须是 JSON 对象否则整请求报错;`namespace` 经工具上下文折平为上游名;`Read` 工具剥 `pages:""`;`status:"incomplete"` 的历史调用整项丢弃并告警 | `providers/transform_codex_anthropic.rs:532-567`、`providers/transform_codex_anthropic.rs:514-529`、`providers/transform_responses.rs:270-297` |
| `{type:"custom_tool_call", call_id, name, input}` | assistant `tool_use` | input 原样包成 `{"input": <input>}` 单键对象 | `providers/transform_codex_anthropic.rs:568-589` |
| `{type:"tool_search_call", call_id, arguments}` | assistant `tool_use`(name=`tool_search`) | arguments 非对象时回退 `{}` | `providers/transform_codex_anthropic.rs:590-611` |
| `{type:"function_call_output" \| "custom_tool_call_output" \| "tool_search_output", call_id, output}` | user `tool_result`(`tool_use_id`=call_id) | output 形态分解见下 | `providers/transform_codex_anthropic.rs:612-624`、`providers/transform_codex_anthropic.rs:729-809` |
| 顶层 `{type:"input_text"}` / `{type:"input_image"}`(无 role 的裸项) | user text / image 块 | 即"整个 input 就是本轮 prompt"的简化形态 | `providers/transform_codex_anthropic.rs:625-641` |
| `{type:"reasoning", encrypted_content}` | assistant thinking/redacted_thinking 块 | 仅识别本桥自有信封(见下);解不开(外来密文/无签名)→ 整项丢弃 | `providers/transform_codex_anthropic.rs:643-651`、`providers/transform_codex_anthropic.rs:71-99` |
| `{role:"user"/"assistant", content: 字符串或 parts 数组}` | 对应 role 的 text/image/document 块 | content parts:input_text/output_text→text;refusal→text(取 refusal 文本);input_image→image;input_file→document;未知 part 类型丢弃;空/纯空白文本丢弃(Anthropic 对空 text 块 400) | `providers/transform_codex_anthropic.rs:653-717`、`providers/transform_codex_anthropic.rs:1106-1108` |
| 其余未知 type 且无 role 的项 | 无 | 静默丢弃 | `providers/transform_codex_anthropic.rs:531-718`(match 兜底臂) |

tool_result 的 output 分解(`tool_result_content_from_responses_item`,`providers/transform_codex_anthropic.rs:729-809`):

- 字符串 → 直接作为 tool_result.content(字符串形态);
- 数组 → 块数组:`input_text/output_text` 取 text(等于 `[cc-switch:tool-result-error]` 标记的 → 置 `is_error:true` 且该块不进 content,标记常量在 `providers/transform_responses.rs:25`);`input_image`→image 块;`input_file`→document 块;其余未知 part 以规范化 JSON 文本块保底;
- 嵌了图片的非原生形态(JSON 字符串里的 MCP image 块/Chat image_url/整串 data URL 等)→ 剥出图片块 + 剩余文本,超限媒体截断并打 `[cc-switch: omitted N bytes]` 标记(`providers/transform_codex_anthropic.rs:815-846`、`tool_media.rs` 经由 `strip_and_clamp_media_from_tool_value`);
- output 缺失 → 整项以规范化 JSON 文本兜底(不丢 call_id 配对)。

图片/文档块转换:

- `input_image.image_url`(字符串或 `{url}`)→ data: URL 拆 base64 source,http(s) URL 用 url source,其余丢弃(`providers/transform_codex_anthropic.rs:1182-1219`);
- `input_file` → `file_url`(http/https)为 url source;`file_data`(data:)为 base64 source;`filename` 映射 `title`(`providers/transform_codex_anthropic.rs:1222-1259`)。

thinking 桥接信封(响应向生成、请求向回放,闭环见 §2.2):签名 thinking 块/redacted_thinking 块整体 JSON → base64url(无填充)→ 前缀 `ccswitch-anthropic-thinking-v1:` 装进 responses `reasoning.encrypted_content`;请求向按前缀+签名校验解码回放(`providers/transform_codex_anthropic.rs:28`、`providers/transform_codex_anthropic.rs:71-99`、`providers/transform_codex_anthropic.rs:101-118`)。**本仓决定**:逐字节沿用该前缀与编码(差异点 §6-D6)。

| responses tool_choice | Anthropic tool_choice |
|---|---|
| `"required"` | `{"type":"any"}` |

### 1.4 `reasoning.effort` → thinking(`providers/transform_codex_anthropic.rs:298-367`)

预算表(`effort_to_thinking_budget`,`providers/transform_codex_anthropic.rs:36-46`;大小写不敏感、trim):

| effort | budget_tokens |
|---|---|
| minimal / low | 2048 |
| medium | 8192 |
| high | 16384 |
| xhigh / max / ultra | 24576 |
| (未识别值) | 不启用 thinking,保持普通采样 |

判定链(按序):

1. **工具史闸门**:末轮是 tool_result 续轮时,仅当紧邻的前一条 assistant 轮含签名 thinking/redacted_thinking 块且其 tool_use id 集合与 tool_result id 完全配对,才允许 thinking(Anthropic 要求工具循环内回放签名思考块);闸门不过 = 本轮 thinking 关(`trailing_turn_supports_thinking`,`providers/transform_codex_anthropic.rs:295`、`providers/transform_codex_anthropic.rs:1013-1070`)。
2. 显式关闭(effort = none/off/disabled)→ `thinking:{"type":"disabled"}`(`providers/transform_codex_anthropic.rs:58-66`、`343-344`)。
3. 有预算 → `thinking:{"type":"enabled","budget_tokens":B}`;B 钳到 ≤ max_tokens/2(给可见回答留一半),钳后 <1024(Anthropic 下限)则整轮关 thinking、不抬 max_tokens(`providers/transform_codex_anthropic.rs:345-359`、`362-367`)。
4. thinking 启用期间 temperature/top_p 不透传(§1.1)。

参考实现另有按模型名的 adaptive thinking 分支(claude-sonnet-5 等 adaptive 模型 → `{"type":"adaptive"}` + `output_config.effort`,`providers/transform_codex_anthropic.rs:301-342`)。**本仓决定**:不移植该模型名启发——三家目标(GLM/DeepSeek/Kimi)均非该名单模型,车道永不产出 `adaptive`/`output_config`(差异点 §6-D4)。

### 1.5 消息规范化(翻译内、发上游前,`providers/transform_codex_anthropic.rs:276-296`)

Anthropic 对 messages 的硬约束逐条兜底:

1. `drop_incomplete_tool_turns`:压缩/续接历史里不成对的 assistant tool_use↔user tool_result 整轮剔除;不成对 user 消息里残留的孤儿 tool_result 块剔除(`providers/transform_codex_anthropic.rs:926-983`);
2. 空消息(内容全被过滤后 content 空)剔除(`drop_empty_messages`,`providers/transform_codex_anthropic.rs:1112-1119`);
3. 首条必须是 user:否则头部插合成 user 消息 `"(continuing the conversation)"`(`ensure_leading_user_message`,`providers/transform_codex_anthropic.rs:904-919`);
4. 全空(如 input 只剩解不开的 reasoning)→ 显式报错 `InvalidRequest`,不留给上游 400(`providers/transform_codex_anthropic.rs:283-294`);
5. 末条 assistant 的尾随空白文本 trim/剔除(Anthropic 拒绝 prefill 尾空白;codex 常在 tool_use 边上带空 assistant 文本)(`trim_trailing_assistant_text`,`providers/transform_codex_anthropic.rs:288`、`1075-1100`)。

### 1.6 翻译后的前向器处理(译文之上的再加工,顺序即执行序)

| 步骤 | 规则 | 出处 |
|---|---|---|
| `[1M]` 标记 | 译出 model 名尾带 `[1m]` → 剥后缀 + 置旗标,出站加 `anthropic-beta: context-1m-2025-08-07` | `forwarder.rs:1592-1603`、`forwarder.rs:2009-2019` |
| Claude Code 身份模拟(可选开关,默认关) | system 前插 Claude Code 身份行(数组化,幂等);UA 换 claude-cli;x-app: cli;beta 加 claude-code-20250219 | `forwarder.rs:1443-1454`、`forwarder.rs:2987-3021`、`forwarder.rs:1917-1923`、`forwarder.rs:2224-2227` |
| prompt cache 断点注入 | **恒开**(独立于全局优化器开关,仅尊重专用子开关):Anthropic cache_control 断点预算 4 个,注入顺序 tools 末尾 → system 末尾(字符串 system 先数组化)→ 最新一条可缓存消息的最后一个非 thinking 块;TTL 统一 5m;既有断点 >4 个则不动交给上游裁决 | `forwarder.rs:1607-1615`、`forwarder.rs:3105-3116`、`cache_injector.rs:12-80` |

**本仓决定**:cache 断点注入跟随参考实现(恒开、预算 4、5m TTL)——codex 请求不带 Anthropic cache_control,不注入则每轮工具循环全价重付 system/tools/历史;三家目标(智谱/DeepSeek/Kimi)Anthropic 方言端点均支持标准 cache_control(既有 CC 车道已在用)。`[1M]` 剥离与身份模拟照抄;身份模拟默认关(参考实现同)。

### 1.7 未知字段策略(票面必答题)

- **翻译分支(Anthropic 目标)**:参考实现是**白名单构造**——`store/include/service_tier/metadata/prompt_cache_key` 等已知 responses 专有字段与一切未知顶层字段都不进上游体,也不报错(`providers/transform_codex_anthropic.rs:228-439` 构造事实;`providers/transform_codex_anthropic.rs:2421-2436` 测试钉死四个字段)。Anthropic 方言对这些字段没有承载位,透传硬塞是否触发上游 400 在参考实现中无证据(仓库规矩:不猜上游容忍度)。
- **本仓决定**:翻译分支跟随白名单构造,但**被丢弃的未知顶层字段名记一条 dock 告警事件**(形状漂移观察,服务 D7"先记账"方针);"透传不丢弃"的完整落地在原生透传分支(dialect=openai_responses:整体逐字节透传,仅 model 改写 + 鉴权注入,未知字段原样达上游)与 input 项级(未知 part 以规范化 JSON 文本块保底,§1.2)。差异点 §6-D2。

## 3. 鉴权与头

### 3.1 入站:占位凭证剥除

- 认证类头(`authorization` / `x-api-key` / `x-goog-api-key`)在**原始位置**被替换为供应商真实认证头;首个位置之外的其余认证头直接丢弃;客户端完全没带认证头时,真实认证头追加到头部表末尾(`forwarder.rs:2082-2105`、`2201-2206`)。
- codex 配置里的占位密钥(codex 侧 env)因此永远不会抵达上游;托管账号场景还有 fail-closed 闸:出站头里检出 `PROXY_MANAGED` 占位且目标是托管上游(chatgpt.com/backend-api/codex、githubcopilot.com、api.x.ai/v1)→ 直接报认证错误,绝不发出去(`forwarder.rs:40`、`3482-3518`)。
- **本仓语境**:渡口既有车道同机制(`internal/dock/headers.go:47-51`:入站 Authorization/x-api-key 一律删,出站只认渡口真钥);翻译车道沿用同一机制与 T39 纪律(真钥只进出站头,永不入日志/账本/错误文本)。

### 3.2 出站:真实密钥注入(Anthropic 线协议供应商)

**参考实现没有此路径**:路由表(supra)无任何 GET responses 路由,也无 `{id}` 通配路由;codex 以无状态方式运行(store:false,会话状态在本地 rollout 文件),从不回查历史 response。**本仓决定**:同样不实现;未匹配路径按渡口通用 404 处理(差异点 §6-D1)。

## 5. model 字段改写规则

改写三原则(本仓,源自 spec 决策 1/3):**逐请求**(每请求读内存态活跃供应商,切换零写盘 D5)、**按供应商条目的模型位映射**、**未知名透传 + 记告警事件,绝不静默替换**。

### 5.1 改写时机与链路(参考实现)

```
入站 responses body
  → 通用模型映射(按条目 env 档位键)         forwarder.rs:1248-1255 / model_mapper.rs:119-145
  → codex 目录保真(目录内模型保留)           providers/codex.rs:501-517(在翻译前,forwarder.rs:1563)
  → responses→Anthropic 翻译(model 原样透传) providers/transform_codex_anthropic.rs:234-242
  → [1M] 后缀剥离(+context-1m beta)          forwarder.rs:1592-1603
  → 出站(model 真值刷新供记账)               forwarder.rs:1701-1708
```

参考实现两段改写的判定:

- **档位映射**(`model_mapper.rs:69-113`):模型名**子串包含**(大小写不敏感)命中 fable/haiku/opus/sonnet → 对应档位值(fable 未配时降 opus 档);子代理模型名(剥 [1M] 后比对)原样保留;其余 → `ANTHROPIC_MODEL` 默认档(未配任何映射则整体不动)。**未知名被静默替换成 default**(测试 `model_mapper.rs:336-342`)。
- **codex 目录保真**(`providers/codex.rs:501-517`):请求模型 ∈ 条目 modelCatalog.models 的 model 集 → 保留不换;否则换成条目上游模型(settings.model 或 config TOML 的 model;`providers/codex.rs:447-466`)。
- **[1M]**:模型名尾缀 `[1m]`(大小写不敏感)本地能力标记,上游不认 → 剥后缀 + 注入 `anthropic-beta: context-1m-2025-08-07`(`forwarder.rs:1592-1603`、`model_mapper.rs:149-172`)。

### 5.2 CC 档位键(既有,车道沿用)

渡口上游条目既有档位键 `default / opus / sonnet / haiku`(spec 决策 1);既有 `/v1/messages` 车道的判定与兜底在 `internal/dock/rewrite.go:102-128`(精确别名键 + 值域真名透传 + default 兜底)。**本仓决定**:CC 车道行为零变化(D11);responses 车道不使用 CC 档位键——codex 请求的模型名不表达 Claude 档位语义,硬套子串判定会把 codex 模型名误判(如含 "haiku" 字样的第三方名)。CC 档位键仅在 `/v1/messages` 车道生效,两车道同读活跃供应商条目、各自判定。

### 5.3 codex 主模型键(本役新增)

- 条目模型位映射新增 **codex 主模型键**(spec 决策 1);dialect=codex 可用性推导见决策 1(anthropic→需翻译;openai_responses→原生透传)。
- responses 车道逐请求改写规则(**本仓决定**,采纳参考实现的目录保真语义):
  1. 请求 model(剥 [1M] 后)∈ 活跃供应商条目的已知模型集(主模型键值 + 条目模型位全部值域)→ **原样透传**(已知真名,子代理/用户自选模型精确保留;对照 `providers/codex.rs:509-512`);
  2. 否则 → 改写为 **codex 主模型键的目标名**(对照 `providers/codex.rs:514-516`);
  3. 主模型键未配置 → **透传原文 + 记告警事件**(见 5.4,不静默替换、不造空模型名;防御姿态同 `internal/dock/rewrite.go:122-127`)。

### 5.4 未知模型名策略(本仓决策,与参考实现相异)

未知名 = 既不在已知模型集、又无主模型键可换(或键空)。**本仓决定 = 透传原文 + dock 告警事件**(事件含 lane、原模型名、活跃供应商名),**不**沿用参考实现的静默 default 替换(`model_mapper.rs:107-109`),也不沿用既有 CC 车道的 default 兜底(那是 CC 语义,codex 语义下换模型等于换掉整个会话人格且 codex 本地会话状态按模型名组织)。差异点 §6-D3。

### 5.5 [1M] 标记

翻译分支照抄参考实现:译出 model 尾带 `[1m]` → 剥后缀 + context-1m beta(`forwarder.rs:1592-1603`)。原生透传分支:codex 不发此标记,无需处理。

### 5.6 GLM 目标 thinking:disabled 落点(D8/ADR-0015,**本仓决定**)

- **触发条件**:活跃供应商 = 智谱 GLM 的 Anthropic 方言端点(dialect=anthropic)。原生 responses 分支(dialect=openai_responses,如智谱 /api/v1)不注入——该分支非 Anthropic 方言,无 thinking 字段。
- **落点**:请求向翻译完成之后的"按目标供应商再加工"段——与 model 改写同段(逐请求、序列化之前),即:

```
responses 翻译产物(Anthropic 形状,thinking 已按 §1.4 由 effort 推导)
  → [GLM 目标] thinking 强制 {"type":"disabled"}(无条件覆盖,无论推导结果)
  → [GLM 目标] 若翻译产物含 output_config(仅 adaptive 分支会产生,本仓已裁不移植,§6-D4;防御性一并剥除)
  → cache 断点注入(§1.6)→ 出站定稿
```

- **理由**:①这是目标上游的属性,不是方言翻译的属性——放在纯翻译器里会把供应商知识塞进协议层;②无条件覆盖对推导链全形态(enabled/disabled/缺省)幂等,满足 D8 的"必须";③与 forced tool_choice 关 thinking 时剥 output_config 的参考先例同构(`providers/transform_codex_anthropic.rs:415-422`)。
- 参考实现**没有**针对 GLM Anthropic 目标的 thinking 强制(其智谱接入走原生 responses 直连,`providers/codex.rs:342-350`)。差异点 §6-D7。
