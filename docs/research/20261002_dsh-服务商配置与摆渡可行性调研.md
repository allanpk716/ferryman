## 2. 服务商配置全景（问题一）

### 2.1 四层配置面（从浅到深）

| 层 | 入口 | 适用 | 落盘 |
|---|---|---|---|
| ① Web UI 内置供应商 | Settings → Models → 选 `anthropic`/`openai`/`moonshotai`(Kimi)/`zai`(GLM)… 填 key | 直连官方端点 | key 进 `~/.dsh/.credentials.yaml`（只写不读回），路由进 profile 的 `cordis.patch.yml` |
| ② Web UI 自定义网关 | "Custom model API"：Provider ID＋baseURL＋**API 协议三选一**＋凭据＋模型清单 | 中转/自建/渡口这类网关 | 同上；协议枚举 `openai-completions` / `openai-responses` / `anthropic-messages` |
| ③ 直编 `cordis.patch.yml` | `$DSH_HOME/profiles/<profile>/cordis.patch.yml` | 全部字段：compat 开关、reasoningEfforts、headers、retryPolicy | 就是 UI 写的同一份文档 |
| ④ 环境变量 | `DEEPSEEK_API_KEY`／`DEEPSEEK_BASE_URL`（仅直连路由）；`HTTPS_PROXY` 等标准代理变量（`~/.dsh/.env`） | 脚本化/headless | — |

要点：

- **Provider ID 永久**（请求、会话记录、模型默认、凭据引用都用它），改名＝新建＋删旧。
- 模型发现：openai 系走 `GET {baseURL}/models`；anthropic 走 `/v1/models?limit=1000`（不翻页，>1000 手补）。
- 一个供应商只说一种协议；双协议网关要拆两条路由。

### 2.2 两个 LLM 适配器（并存、路由名不冲突）

| | `dsh-llm-deepseek`（直连孪生） | `dsh-llm-pi-ai`（多供应商孪生） |
|---|---|---|
| 路由名 | `deepseek-official`（API key）/ `deepseek-account`（OAuth 账号） | `providers` 字典每键一路由 |
| 线协议 | DeepSeek Messages（Anthropic＋私有扩展：`output_config.effort`、`thinking` 块、`tool_addition` 块、files-api 等 beta 头） | pi-ai 目录或手声明：`openai-completions` / `openai-responses` / `anthropic-messages` |
| baseURL 覆盖 | `baseURL` 配置 → `$DEEPSEEK_BASE_URL` → 官方根 | 每路由 `baseURL`（必填于手声明路由） |
| 内置目录 | deepseek-flash / deepseek-v4-pro（1M 窗） | anthropic、openai、deepseek、zai、moonshotai、openrouter、azure 等（含 zai 专属 thinking 格式与 `zaiToolStream: withhold` 怪癖知识） |
| 网关怪癖修正 | 无（协议固定） | `compat` 开关：`supportsDeveloperRole`、`maxTokensField`、`thinkingFormat`（含 `deepseek`）、`thinkingTokenBudgetField`、`cacheControlFormat: anthropic`（OpenAI 线上认 Anthropic 式缓存标记的中转）等，路由级/模型级 |
| 凭据 | `apiKeyEnv` 引用逐请求解析；账号模式走 credential 平台 | `apiKeyEnv` 或 OAuth 登录（存 `llm-pi-ai/<provider>`，跨进程刷新锁） |
| 会话身份上线 | **`x-deepseek-harness-session-id` 头**（每请求，adapter.ts:129） | `GenerateOptions.sessionId` 传入 pi-ai `streamSimple`；落到线上什么形态**待 spike**（pi-ai 可能把 sessionId 映射进 provider metadata） |
| 出错码 | AUTH/QUOTA/RATE_LIMIT/CONTEXT_WINDOW_EXCEEDED…（稳定码） | 同左＋`INVALID_CREDENTIAL`/`MISSING_CREDENTIAL`/`UNKNOWN_MODEL`；pi-ai 错误事件**不带稳定 HTTP 状态码** |
| 请求通道 | 裸 `fetch`（不吃 `@cordisjs/plugin-http` 的共享代理/拦截配置） | pi-ai 自有 transport |

### 2.3 与渡口对接的两种接法

**接法甲（推荐）：pi-ai 自定义路由说 `anthropic-messages` 指渡口。**

```yaml
# ~/.dsh/profiles/web/cordis.patch.yml（Web UI ②等价产物）
- id: llm-pi-ai
  config:
    providers:
      ferryman-dock:
        apiKeyEnv: FERRYMAN_DOCK_TOKEN   # 渡口入站占位令牌（不校验、绑本机）
        api: anthropic-messages
        baseURL: http://127.0.0.1:15722
        models:
          - id: glm-5.3                 # 模型名由渡口上游表active决定；可配改写映射
            contextWindow: 200000
```

- dsh 流量变成标准 Anthropic 协议进渡口 CC 车道；**切供应商只翻渡口 `[dock].active`，dsh 侧零写盘**——服务商接管战役的目标拓扑在 dsh 上天然成立，一次性配置即可。
- 渡口侧需新增识别：按 `User-Agent: deepseek-harness/...` 区分 dsh 与 CC 流量（形态漂移告警的观察对象也跟着扩展）。
- 改写五件对 dsh 流量的适用性需差分验证：`[1M]` 剥除、六键模型档映射是 CC 特有；**anthropic-beta 重建（确保含 claude-code 标记）对 dsh 反而不该加**——这条按"出现第六件要么缺陷要么过 ADR"的纪律，dsh 车道要么独立改写集要么过 ADR。

**接法乙：`deepseek-official` 路由改 baseURL 指渡口。** 白送逐请求 `x-deepseek-harness-session-id` 头（渡口捕获键第三来源，现成），但线上带 DeepSeek 私有扩展（`output_config.effort`、thinking/tool_addition 块、files-api beta 头）——上游是 GLM/Kimi 时大概率被拒，渡口得加"剥 dsh 方言"新改写件（成本高于接法甲，仅当想要免费会话头时再评估）。

### 2.4 凭据与配置文件清单（接管手术的写盘面）

| 文件 | 内容 |
|---|---|
| `~/.dsh/.credentials.yaml` | 全部凭据（只写、UI 只见脱敏描述符） |
| `~/.dsh/profiles/<名>/cordis.patch.yml` | 供应商路由（UI 与手编同一份） |
| `~/.dsh/profiles/<名>/package.json`＋`dsh.profile` | 外挂插件依赖与 bundle 序 |
| `~/.dsh/.env` | key 与代理变量（gitignored，`$DSH_HOME` 级） |

对比 CC/codex 接管（写 orca 家三份配置）：dsh 只有一份 patch＋一份凭据库，且**不走接管也能手工配**——`ferryman provider apply` 的 dsh 分支是"锦上添花"而非必需。

## 3. 摆渡可行性（问题二）

### 3.1 Ferryman 五大件 × dsh 落点总表

| Ferryman 件 | dsh 原生机制 | 状态 |
|---|---|---|
| 守望（watch） | 会话日志 `~/.dsh/sessions/--<规范化cwd>--/<转义id>/session.vN.jsonl(.zstd)`，追加式、不可变代；`compression: 'none'` 一行配置可关压缩（外部读者直接吃文本行）；默认 zstd＝checksummed 帧拼接，Go 侧 klauspost/compress 可解 | ✅ 布局已核实；规范化目录名精确规则实现期对 `src/format.ts` |
| 台账（ledger） | 每事件带 `time`（内容时钟现成）；`assistant/message` 事件携带 `TokenUsage`：inputTokens（仅未缓存）/outputTokens/cacheReadTokens?/cacheWriteTokens? **不相交口径，计费输入＝三者之和——与 Ferryman 四列口径同构**；子代理是独立会话目录、父头里有 `subagent/catalog` 子女目录引用（族系/判活/子代理记账有数据源） | ✅ |
| 闸门（gate） | 原生：`agent/pre-step` 瀑布返回 `reject`＝提交前拦截、不开步、零 token（CC 桥的 deny 也映到它）；桥：`dsh-hooks-claude-code` 直接跑现有 CC hooks.json 的 UserPromptSubmit | ✅ 两路都核实（0916 调研＋本次源码） |
| 归还（restore） | 原生：`agent/created` 串行**awaited** 初始化，`agent.inject()` 播种上下文——赶得上首请求；桥：SessionStart 走 detached 注入，**可能错过首请求**（官方已知局限） | ✅ 原生路可靠；桥路降级 |
| 渡口＋心跳 | 见 §2.3：pi-ai 路由指渡口后，捕获-重放机械与 CC 完全同构；**捕获键**＝体 `metadata.session_id` → 头 `X-Claude-Code-Session-Id` → `x-deepseek-harness-session-id`（P2-2 已加第三回落） | ⚠️ pi-ai 路由无键上线（§3.4 结案）——捕获归因空，待接法乙/P2-4 插件 |
| 记账 | 走渡口即得 dock 科目（四列、改写前后模型名、延迟、状态码）；会话日志 usage 是第二独立源可对账 | ✅ |
| 等待窗口/问询守望 | 子代理有独立会话与 lineage 事件；CC 特有的"async 文案"判据不移植，dsh 侧判活信号重选（`agent/status`→idle、`agent/disposed`、子女目录写入） | ⚠️ 设计期待定（与 codex 轨同等待遇，不阻塞主线） |

### 3.2 路线 A：零代码 MVP（配置 + CC 钩子桥）

1. §2.3 接法甲配一条渡口路由（手工或 Web UI）。
2. profile 挂官方桥：`dsh plugin --profile web add @deepseek-ai/dsh-hooks-claude-code`，`configPath` 指 Ferryman 给 dsh 单独发的 hooks.json（现有 CC 钩子脚本原样复用：UserPromptSubmit 问闸门、block→deny）。
3. 守望加 dsh 会话根（zstd 解压或 profile 里 `compression: 'none'`）。

桥的已知硬伤（官方 README 逐条列明，皆可接受或不碰）：

- SessionStart 注入 detached——**归还赶不上首请求**；MVP 期归还可用"新会话第一句手打 /restore 或待续 prompt 引导"过渡，或接受首请求后一拍注入。
- `transcript_path` 恒空串（持久化缝不暴露工件路径）——Ferryman 钩子本就不解析会话文件（台账外部记账），无碰。
- UserPromptSubmit 只认 JSON additionalContext（Ferryman 不用注入面）；桥默认超时 600s，但**尊重 hooks.json 里每钩子自设 timeout**（`defaultTimeoutMs` 仅兜底）——钩子侧显式设 2-3s 即可。
- 一进程一份 configPath、启动读一次——Ferryman 的 dsh hooks.json 独立成文件即可，无分层发现需求。
- 钩子失败/配置坏＝记日志继续（fail-open）——与 CC/Codex 钩子原生语义一致 ✅。

### 3.3 路线 B：原生插件 `ferryman-dsh`（长期正确形态）

插件＝导出 `apply(ctx)` 的 TS 模块，`dsh plugin --profile web add github:allanpk716/ferryman-dsh` 或 `file:./` 安装。订阅规范事件面（无序列化边界、全量 ctx、类型化返回——官方明言"桥能做的原生插件都能做，且更强"）：

| 订阅 | 用途 |
|---|---|
| `agent/pre-step` | 闸门：问 daemon → `reject`（带用户可见理由）或 `enter` |
| `agent/created`（awaited） | 归还：同 Agent＋同 cwd 的最新交接 MD 经 `agent.inject()` 播种——**赶首请求，补桥的 detached 硬伤** |
| `session/event` | 台账活动上报（替代/补充文件守望；含 turn/start、user/message、assistant/message 带 usage、tool/result、compaction/*） |
| `agent/disposed`／`agent/status` | 判活与等待窗口信号 |

插件同时可把"渡口路由健康检查/版本对账"做成挂载自检（社区先例：ZhijiangTang/dsh-handoff 挂载即真实管道自检打证据）。

规模估计：宿主侧几百行 TS（对照 dsh-handoff 家族皆为单包零依赖级）；Ferryman 侧加一个 dsh agent 适配（ledger/gate 复用现有 HTTP 面）。

**插件不做的事**：LLM 路由（原生配置已够）、心跳/捕获重放（渡口侧机械）、摆渡执行器（daemon 侧）——插件只是"dsh 轨的钩子面"，架构上等同 CC 轨的 hooks.json，不是第二个 daemon。

### 3.4 会话键捕获：心跳关键路径的三方案

1. **pi-ai sessionId 落点**（首选待验）：`GenerateOptions.sessionId` 已传入 pi-ai streamSimple；若 pi-ai 把它映到 Anthropic 线 `metadata` 或某头，渡口 `ExtractSessionID` 加第三回落即可。spike＝起 mock 端点抓 dsh→pi-ai anthropic-messages 请求看线。
2. **渡口侧时间关联**（兜底）：单机单活跃 dsh 会话时按"最近一次到达的 dsh UA 流量"记账面关联（脆弱，多会话并发失真——只作 spike 失败时的降级）。
3. **接法乙**（不推荐起步）：直连路由 baseURL 指渡口白拿会话头，代价是剥方言改写件＋ADR。

> **P2-2 spike 结案（2026-10-03，方案 1 落空、源码四源＋账面实证）**：pi-ai（0.87.1 与 main 同）anthropic-messages **不把 sessionId 映进请求体**——体的 `metadata` 只有 `user_id` 一条通路（dsh 不传）；sessionId 仅映 `x-session-affinity`/`x-session-id` 头，且开关 `sendSessionAffinityHeaders` 被 dsh 侧 llm-pi-ai catalog 标 `'withhold'`（手建路由不可配）。10-02 PR #4 验收的"捕获键零改动就位"是把自家 CC 会话（af22e212）记账行误读为 dsh 行——当日 dsh 流量两行 session_id 恒空（与文件 usage 四列签名交叉对上，确系 dsh 行）。**键事实**：dsh 唯一带会话键上线的通道＝llm-deepseek 适配器的 `x-deepseek-harness-session-id` 头（值=会话头行 id `session-<uuid>`，与守望/台账现行键同源零换算）。渡口已加该头为 `ExtractSessionID` 第三回落（P2-2 落地）；当前接管路由 llm-pi-ai 不发该头——dsh 流量渡口捕获归因仍空，解锁路径＝接法乙（方案 3）或 P2-4 原生插件 `session/event` 直报。方案 2 维持弃用。
