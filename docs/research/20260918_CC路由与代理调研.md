### 2.2 当前供应商（Claude 链路）

DB providers 表中 id=43b968b8（名字 **GLM Coding**）：

- `ANTHROPIC_BASE_URL: https://open.bigmodel.cn/api/anthropic`（智谱 Anthropic 兼容端点，日志里每次转发的目标与此一致）
- `ANTHROPIC_AUTH_TOKEN: 7e2f***`（真实密钥只在这里）
- 供应商侧模型映射（= 代理改写的依据）：

  - **default（ANTHROPIC_MODEL）→ `glm-5.3-flash[1M]`** ← 关键，见 §2.5

- DB 里另存有 OpenRouter（`sk-G***`）、aihubmix（`sk-G***`）、旧版智谱（`be4e***`）等备用供应商配置。

### 2.3 日志记不记请求体？——不记

日志每次转发只有一行 INFO：

```
[Claude] >>> 请求目标: https://open.bigmodel.cn/api/anthropic/v1/messages (model=GLM-5.3)
```

8MB 日志里没有出现过任何请求/响应 body。ERROR 级为零，WARN 只有 `[USG-002] 模型定价未找到，成本将记为 0` 这一类计价提示。

DB 的 `proxy_request_logs` 表也只存**元数据**：`request_id, provider_id, app_type, model, request_model, input/output/cache_read/cache_creation tokens, 各项成本, latency_ms, first_token_ms, status_code, error_message, session_id, provider_type, is_streaming`。没有 body 列。

> 也就是说：想抓"CC 原始报文"做字节级重放（设计文档 §3.5 的保真度备胎），CC Switch 现状不提供素材，得自己上旁路监听或改代理。

### 2.4 改不改请求体？——改，且有五处（源码实锤）

对照本机日志模块名拉了上游源码 `src-tauri/src/proxy/`（farion1231/cc-switch main 分支）：

1. **模型映射**（`model_mapper.rs`）：按供应商 env 配置改写 `body.model`。规则=模型名小写后 contains "fable"/"haiku"/"opus"/"sonnet" 分档替换；都不含则试 subagent 名匹配；再不然落 **default（ANTHROPIC_MODEL）**；无配置才原样透传。日志里出站 `glm-5.3-flash`/`GLM-5.3` 而 CC 发的是 `claude-*[1M]`，改写实锤。
2. **剥 `[1M]` 后缀**（`strip_one_m_suffix_for_upstream`）：CC 用 `[1M]` 声明百万上下文，上游不认，转发前剥掉。
3. **认证接管**：源码常量 `PROXY_AUTH_PLACEHOLDER = "PROXY_MANAGED"`——CC 发来的占位令牌在转发时被换成供应商真实密钥。代理对入站请求不校验真实密钥（占位符即可过）。
4. **thinking 整流 / body 白名单过滤 / media 降级**（`thinking_rectifier.rs`、`body_filter.rs`、`media_sanitizer`）：整流 thinking 参数、按白名单过滤私有参数、text-only 模型把图片块换标记。均为条件触发。
5. **cache_control 注入**（`cache_injector.rs`）：优化器开启时在 tools 末/system 末/最新消息最后一个非 thinking block/次新 user 锚点补 `{"type":"ephemeral"}` 断点（上限 4 个，只补缺不删改已有）。**本机日志 8MB 里一条 `[OPT]` 都没有 → 该功能本机未生效**；缓存断点实际全部由 CC 自己带（与实验 README"CC 前缀带 cache_control 断点"一致），GLM 端实测命中正常，不受影响。

### 2.5 对心跳最重要的推论：daemon 必须发 claude-\* 别名，不能发 GLM 真名

设计文档 §3.5 定的路线是"按会话请求形状逐 token 重构，直打 CC Switch 本地代理"。结合 §2.4-1 的映射规则有个坑：

- CC 真实主链路发 `claude-opus-5[1M]`（或 fable）→ 命中 opus/fable 档 → 上游 `GLM-5.3`；
- 若 daemon 直接照抄会话 jsonl 里的 `model` 字段（`GLM-5.3`）发给代理 → "glm-5.3" 不含任何档位关键词 → **落 default 档 → 被改写成 `glm-5.3-flash`** → 换了模型 = 缓存键不同 = 必 miss，还白烧一次全价。

**正确姿势：daemon 发 CC 同款别名**（主链路 `claude-opus-5[1M]` 或 `claude-fable-5[1M]`，两者上游同为 GLM-5.3；子代理链路 `claude-sonnet-5[1M]`），让代理走与真实流量完全相同的映射路径。令牌照抄 `PROXY_MANAGED` 即可。这条必须进 L2 保真度验证清单。

### 2.6 顺带发现：CC Switch 已有现成的 usage 归因

`proxy_request_logs` 带 `session_id` + `request_model`（映射前客户端别名）+ `model`（映射后上游真值）+ 四类 token 数 + 成本；另有 `session_log_sync`/`session_usage_dedup` 表（`data_source` 含 'proxy'）说明它已经在解析 CC 会话 jsonl 做用量对账。Ferryman 的 T41 台账将来可与它对数（只读），不必自己从零归因。

## 3. 实验资产盘点（`C:\WorkSpace\agent\Ferryman\experiments\cache-ttl\`）

### 3.1 套件结构

- `README.md`：通用 TTL 测量方法论。四问（闲置 TTL / 命中续命 / 部分命中 / 跨会话共享）、三轨（agent=probe_pi / CC=probe_cc / API=probe_api）、五步流程、防污染铁律（每臂独立前缀、一写一探、记 actual_gap、×3 起步跨天复测、阈值 0.85+看形态）。
- `probe_api.py`：OpenAI 兼容端点直打。**可复用件**：`build_prefix()`（按 arm_id 确定性生成字节级相同的前缀）、`sleep_until()` 分片睡眠、`extract_cached()` 三家字段别名兼容、状态落盘断点续跑。
- `probe_cc.py`：CC 真实链路轨。

### 3.2 CC 轨怎么构造请求（现状做法）

不手工拼 Anthropic 报文，而是**驱使真 CC 发请求**：

1. 每臂独立 scratch 工作目录 + `claude -p --session-id <uuid>` 新会话，stdin 灌长资料（默认 24000 字符 ≈16k token，叠加 CC 自身 system+tools 约 40k token 前缀）；
2. 干等后 `claude -p --resume <sid>` 问一句探针；
3. 从 `~/.claude/projects/<munged-cwd>/<session-id>.jsonl` 读每条 assistant 记录的 `message.usage`：`cache_read_input_tokens / cache_creation_input_tokens / input_tokens / output_tokens`；
4. cwd→目录名规则：`re.sub(r"[^A-Za-z0-9]", "-", cwd路径)`（如 `C--WorkSpace-agent-Ferryman`）。

### 3.3 已知 CC 请求形状细节（实测来源）

- CC 前缀 = 自身 system + tools 定义 + 消息序列，实验中实测约 40k token 量级，自带 cache_control 断点（写入轮 usage 样本：`input 40325 / cacheRead 1024`；10 分钟后探针轮 `input 29 / cacheRead 41344`——整段前缀命中，二值形态）。
- 会话 jsonl 的 assistant 记录结构：`{type:"assistant", uuid, timestamp, message:{id, model, role, content[...], usage:{input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens, output_tokens_details.thinking_tokens, server_tool_use}}}`。
- 实测战果（详见 `docs/20260917_1630_GLM缓存TTL实测与心跳保温可行性_实验报告.md`）：GLM-5.3 **≤10 分钟确定性命中（17/17）、11 分钟起风险（11min 2/4，12min 3/7）、≥30 分钟确定性失效，与客户端无关；命中刷新计时 → 心跳每 ~8min 一跳可行**。

### 3.4 可直接复用到"守护进程重构 CC 请求"的件

| 件 | 出处 | 复用方式 |
|---|---|---|
| TTL/续命参数与"间隔-命中率曲线" | README + 已有战果 | policy calculator 的参数来源（config.toml 带 measured_at） |
| usage 字段解析（三别名兼容） | probe_api.extract_cached / probe_cc.parse_cc_usage | 心跳实收 cacheRead 的判定代码可直接移植 |
| 稳定前缀生成（确定性、字节级可复现） | build_prefix | 仅适用于**合成**前缀；真会话前缀须从 jsonl 重构（设计文档 §3.5 已定） |
| munged-cwd 与 session 文件定位 | probe_cc.cc_projects_dir | daemon 找会话文件现成可用 |

**注意**：probe_cc 轨是"驱使 CC 发请求"，体外重放是"daemon 自己拼 Anthropic 报文直打代理"——后者**没有现成代码**，system 块数组形态、tools 数组、消息序列化、断点位置这些细节只能走 §3.5 的保真度备胎（旁路抓一次真实报文）或 L2 抓包比对来定，experiments 里没有可直接抄的报文模板。

## 4. 模型名来源（会话 jsonl）

- assistant 消息记录**带 `model` 字段**，值为**上游响应回显的模型名**。抽样三处：
  - Ferryman 主会话 `5614fa42….jsonl`：`"model":"GLM-5.3"`
  - CC 轨实验会话（10min-r0）：`"model":"GLM-5.3"`
  - 8 月旧会话（NUC10 目录）：`"model":"glm-5.3"`（当时链路不同，大小写随上游回显）
- 对照：这些名字是**代理映射后的上游真值**（日志出站同名），不是 CC 发出的 `claude-*[1M]` 别名。jsonl 里**没有**存 CC 侧别名。
- 心跳要用"与会话一致的模型名"（缓存按模型组织），正确的取用链：
  1. 从 jsonl 读回显名（如 `GLM-5.3`）→ 判定该会话落在哪个上游模型族；
  2. 反查 CC Switch DB 供应商映射（GLM-5.3 ← opus/fable 档）→ 得出应发的客户端别名 `claude-opus-5[1M]`/`claude-fable-5[1M]`；
  3. 也可以直接读 `~/.claude/settings.json` 的 `ANTHROPIC_DEFAULT_*_MODEL`（它就是 CC 发的别名表）——但注意这文件由 CC Switch 接管时改写（`proxy_live_backup.original_config` 存原件），**读时点要新鲜，别缓存**。
- 备选地面真值：`proxy_request_logs.model/request_model` 直接记录了每个请求两个名字，但本轮 Bash 受限未能做行级抽样验证（表结构已确认有这两列）。

## 5. 落点小结（给心跳实现的三句话）

1. 路由就一个入口：`http://127.0.0.1:15721` + `PROXY_MANAGED` 令牌 + claude-\* 别名模型名；真实密钥与映射只在 cc-switch.db 里。
2. 代理会二次改写请求（模型映射/[1M] 剥离/thinking 整流/参数白名单），但**不记请求体**——保真度验证所需的"真实报文"要自抓。
3. 心跳请求的模型名绝不能用 jsonl 回显名直发（会被映射进 flash 档必 miss），必须发 CC 同款别名。
