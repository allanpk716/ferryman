# 后端整体迁 Go（除前端）：单 exe、公式单源、钩子自举

Ferryman 后端（守护进程、闸门、摆渡、账本、report、未来的心跳执行器与时间线查看器）整体用 Go 重写；前端为原生 web 三件套（HTML+JS+CSS+自带单文件图表库），`go:embed` 嵌入 exe。理由：①项目无任何硬 Python 依赖（HTTP/解析/字符串加工全为普通技能，TOML 一个成熟库解决）；②全量统一后公式回归**单源**——此前反对"查看器 Go+主体 Python"的核心论证即公式双份漂移（策略公式 v1→v1.1 这类演进必然出现两边忘改一边）；③单 exe 部署与**钩子自举**（钩子发现守护不在即无窗口后台拉起，当次照旧放行、fail-open 不变；Python 冷启动慢一个量级且闪控制台窗）。

路线四步：时间线查看器（滩头，验证工具链与嵌入）→ 守护核心（守望/闸门/台账/交接库/账本，以现有 164 测试为规格移植）→ 摆渡执行器 → 心跳执行器原生 Go（Python 中从未实现，不造两遍；授权铁律不变：窗口数据门槛+保真实验+用户明确放行）。验收三关：移植测试全绿 / 守护核心与 Python 版在真实会话样例上**逐字段一致**（闸门判定与账本流水）/ observe 模式烧机数天后才切 enforce。烧机通过后 Python 版打最终 tag 存档，随时可回退。明确代价：重写打过仗的代码（R1–R14 终审修复、Windows 怪癖均需重证）与切换期回归风险，以此换长期单源与部署体验。特批调度：**用量落库先以 Python 小补丁落地**（心跳授权的 ≥30 窗口/两周数据门槛在关键路径上，数据钟应于迁移数周间先行）。

## Considered Options

- **混合（Go 查看器 + Python 主体）**：公式两处维护，公式演进时漂移成"两本账"；双工具链同时部署——否决（此为本 ADR 前的推荐项，被用户"全 Go"决策推翻）。
- **维持全 Python**：零重写风险，但 exe 部署/钩子自举体验/公式单源均不可得；用户明确偏好 Go——否决。
- **不烧机直接切**：闸门是日常依赖路径，回归直接砸正常工作流——否决。
