# 同映像多进程下的换装与无窗口拉起（改名让位两步式）

2026-09-22 v0.1.4 生产升级失败暴露两个缺陷：① agent 面 mcp 实例（ADR-0009，用户级注册，CC 会话常驻拉起）以同一 exe 为映像在跑——停旧守护管不到它们，单次 `MoveFileEx(REPLACE_EXISTING)` 对运行中映像必 Access denied（备份已拷、替换被拒、升级必败）；② 失败恢复 `restoreServiceQuiet` 拉起守护时，`launchCmdImpl` 对 cmd.exe 误用 `DETACHED_PROCESS`——cmd.exe 无控制台时执行批处理会**自建可见控制台**，守护常驻一个窗体（零闪窗铁律 af78f82 被破）。且失败现场只活在转瞬即逝的自中继副本 stdout 里，journal 又被清账，事后无痕。

决定三件：

1. **换装改「改名让位」两步式**：旧 exe `MoveFileEx` 改名到备份位（让位即备份，比特相同免拷贝；REPLACE 覆盖同号陈旧备份）→ 新 exe 落位原名。根基是 Windows 固有语义「运行中映像可改名、不可覆盖」（Chrome/VS Code 更新器同款）。
2. **拉起优先 wscript + 隐藏点火 VBS**（Run 键/看门同通道；缺失回落 `CREATE_NO_WINDOW`——对 cmd.exe 这是唯一不建窗的正确旗标）。点火脚本保持「怎么启动 daemon」的唯一出处，update 不另立直拉 exe 的第二套启动知识。
3. **监督者日志落 `<DataDir>/update.log`**：stdout 之外逐行追加留证，失败可追。

> 补记（2026-09-23，v0.2.0 部署事故）：决定一漏了一个分支——**备份名本身也会被运行映像占据**。任何一次换装都把当时存活的 mcp 实例映像改名到 `old-<from>` 上（决定一的自然结果），这些实例随 CC 会话长期存活；于是**同 from 版本第二次升级**（失败重试、同版本排演后真升——当日 13:43 v0.1.5→v0.1.5 排演即毒化了 17:59 的 v0.1.5→v0.2.0）的让位步要 REPLACE 掉 `old-<from>`，撞上「不可覆盖」，Access denied 必败（两次实测+孤立 API 三路二分证实：单项改名全通、组合必拒）。修法：让位被拒且备份位在场时，先把占据者**改名挪到 `old-<from>.stale-<时间戳>-<PID>`**（改名活映像恒可行，名字留在 old-* 域内由 pruneBackups 自动收账——删不动时静默，待进程退出后收走），空出备份位重试让位。回归测试 `TestSwapColonizedBackupStillSwaps`（节映射锁钉住备份位）先红后绿钉死此分支。诊断实录：`Get-Process Path` 显示启动时路径，被改名的进程仍报旧名，极具迷惑性——判定占据者要看「谁在该文件名上活过两次换装」，不能信进程表。

## 与 ADR-0010 的关系

ADR-0010 以「停旧后无运行锁 → 单次原子替换 → 无 exe 缺位窗口」否决了双 rename 草案。该前提被同映像多进程（mcp 实例）击破——单次替换在此拓扑下**永不可行**，权衡翻转：接受两步之间毫秒级缺位窗口（看门/自举在窗口内拉空只会失败，下一轮重试即恢复），换「必然可换装」。ADR-0010 的该前提句作废；其余（锁单飞/journal/停旧/校验/回滚/自中继）不变。落位与复原双败的极端情形如实报警（目标缺位，人工介入），不复原不装死。

## Consequences

- 陈旧同名备份（上次失败遗留）会被让位改名直接覆盖——它不是运行映像。
- 换装后仍在跑的旧映像进程（mcp 实例）不受影响，照旧服务直至其自然退出；新起的进程用新 exe。
- 测试以「节映射句柄」复刻运行映像锁语义（可改名、不可覆盖），前提钉子保证模拟不失真。
