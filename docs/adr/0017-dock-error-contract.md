# 渡口错误契约:响应侧零改写透传,自产错误按流状态分流投递标准形状

状态:已接受(2026-09-28;契约先行成文,五件热修按此契约实施,规格见 docs/superpowers/specs/20260928-dock-error-contract-spec.md)。

## Context

2026-09-28 早晨 CC 两次报 "Connection lost mid-response",根因=守护重启用 `http.Server.Close()` 立即掐断在途 SSE 流——CC 收到的是它无法正确响应的裸断连。证据链:serve.err.log 同秒 `proxy error: context canceled`、账本同刻 502、漂移告警重报、daemon.pid started_at=09:37:14;当天至少 4 轮重启,发起者无日志(悬案,D14 未决)。上游侧当天无 429/5xx(9 月 6311 笔流水仅 200×6303+502×8,502 全为代理自答)——事故全部是渡口自产。同时查明:渡口对上游非 200 响应已是字节级透传,但自产的三类错误(拨号失败回空体 502、上游 200 后挂死无超时、关停掐流无解释)不符合 CC 认识的任何标准形状,截断的流在账本上零痕迹,关停来源无日志。

## Decision

**响应保真(response fidelity)**:上游非 200 的状态码、响应体、响应头零改写透传;`retry-after`/`x-ratelimit-*` 头必须继续透传。理由:CC 的重试机制认标准形状,翻译反而制造 CC 不认识的形状——且 cc-switch v3.20.4 源码级对照确认其错误响应经重建、会丢 retry-after/限流头(是它的毛病),渡口现状透传不劣于它,加冒烟行锁住。管辖范围=上游非 200 响应的转发;渡口自产的流内终止不在此列。响应侧出现任何改写要么是缺陷要么过 ADR。

**渡口自产错误(dock-originated error)**:渡口自身产生的错误一律输出 CC 已认识的标准形状(伪装成 Anthropic 错误),禁止自定义 JSON、禁止裸断连。理由:CC 的重试与报错 UI 只认 Anthropic 形状,裸断连让它无从重试也无从归因(本次事故的界面表现即 "Connection lost mid-response")。按流状态分流投递:

- 首字节未写出(响应头尚未发给 CC)→ HTTP 状态(502/504)+ Anthropic 错误体(`{"type":"error","error":{"type":"api_error","message":...}}`)+ `Retry-After`;
- 流已建立(200 已写、SSE 进行中)→ 先合成一个 Anthropic 流内错误事件(SSE `event: error`)再断连。

**三条声明式残余边界**(不可消除,成文为已知边界):

- 上游已建立流后自己断连/干净 EOF 截断 → 不抢救(与参考实现一致,业界通行),连接断;账本 dock 科目流水行加 `truncated` 标记补观测;
- 非流式请求在排水到期时 200 已写出、body 未传完 → 无合法错误投递通道,收尾=断连+尽力记账(round1 评审新增边界);
- 关停来源日志只覆盖自愿退出路径(/shutdown 端点、托盘退出、Ctrl+C 信号);外部强杀与崩溃无进程内日志机会。

**维持「整流 no-op」**:不移植参考实现的错误恢复件(换家 failover/熔断 circuit-breaker)。本项目换上游纯手动(ADR-0012),自动换家无消费者;「整流」词条的 Avoid 注记维持不变。

## Considered Options

- **翻译上游错误为归一化自造格式**:看似整洁,实则制造 CC 不认识的形状,官方重试/退避失灵——否决,即响应保真所禁。
- **重建错误响应(学 cc-switch)**:重建丢 retry-after/x-ratelimit-* 头,退避信息丢失——否决,这是参考实现的毛病不是目标。
- **上游流中段断连抢救(缓冲重放/重连续传)**:SSE 不可重放,全流缓冲换内存与延迟,参考实现亦不抢救——否决,以 truncated 记账补观测。
- **移植换家/熔断**:换上游纯手动是既有决定(ADR-0012),故障转移是另一量级工程且无消费者——维持 no-op。
- **自产错误用自定义 JSON 带更多诊断字段**:CC 只认 Anthropic 形状,多余字段进不了它的重试决策——否决,诊断走日志与账本。

## Consequences

- 渡口自此的可见行为:上游错误原样到达(CC 官方重试照常)、自产错误必有标准形状与退避提示(CC 可自动重试)、关停/排水收尾带流内解释、截断入账、自愿关停有来源日志——「渡口永不让 CC 看到无解释的断连」。
- 五件热修承接实施:优雅排水(Shutdown 带上限,默认 180 秒——在途实绩 37.9s/11.3s 覆盖有余,到期对流内请求合成错误事件后硬收)、拨号失败错误体(502+错误体+Retry-After 约 5 秒)、首包闸门(仅流式,静默 60 秒判失败回 504)、干净 EOF 观测(truncated 记账)、关停来源落日志;契约条款即其验收基准,冒烟清单见 internal/dock/SMOKE.md。
- 记账与配置面:dock 科目流水行新增 `truncated` 字段仅出现于截断行(缺省不写,读侧宽容忽略);`[dock]` 节新增排水上限键(缺省 180 秒)。
- 请求侧零触碰:快照/改写五件/心跳重放路径不受本契约影响;未来任何响应侧改写(如压缩、重试合成)必须过新 ADR,与「出现第六件要么是缺陷要么过 ADR」同构。
- 事故档案与机器账在 `.xcheck/20260928-103605/`;四轮重启发起者仍未决(D14),热修第 5 件为下次自愿退出路径提供观测。
