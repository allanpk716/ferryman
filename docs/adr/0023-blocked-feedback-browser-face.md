# 被拦反馈住在浏览器侧插件面（双面包），不在宿主侧插件

dsh 消息被闸门拦截时，用户可见反馈（对话区选择框）只能在 DSH 的浏览器侧插件面（dsh.client 双面包）实现——2026-10-06 spike 实证：纯宿主侧插件（ferryman-dsh 现形态，与官方桥同形态）没有任何对话区渲染能力，宿主面用户可见通道唯一是 logger（日志面板），而用户主力使用面是手机 web UI，logger 不可见=零反馈。选择双面包意味着：插件从"纯宿主侧"升为"宿主+浏览器"双半面，被拦原话经宿主插件缓存+Remote 供浏览器侧拉取，按钮动作回落宿主面（followup 代发强续/一键新会话走 daemon 归还链）。

## Considered Options

- **F1 双面包（已选）**：唯一能兑现已定 UX（对话区选择框；Toast 已否决）的路；代价=插件分发形态变化（package.json dsh.client 声明+零依赖 client 产物）、与 DSH 前端内部面（slot 系统/启动 roster）耦合、宿主重启才加载。
- F2 纯文案强化（logger 带原话+两行指路）：零 UI，手机端仍不可见——已作为过渡止血先行落地（票10），不替代 F1。
- F3 会话日志塞自定义 JSON 块：非交互、污染转录，否决。
- F4 等宿主官方提供宿主侧通知面：无限期零反馈，否决。

## Consequences

- DSH 宿主升级可能破坏浏览器半面（slot 名/roster 机制漂移）——升级 DSH 后需复验选择框，失灵只降级回"消息消失+日志面板一行"（拦截本身不受影响，闸门在 daemon 侧）。
- 被拦原话的存活窗口=宿主进程生命周期（拦截时缓存，重启即失，降级为用户手打「强续 <原话>」）。
- 宿主侧插件形态与官方桥保持同构的部分（事件上报/闸门问询）不受本决策影响。
