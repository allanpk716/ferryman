# 升级停顿对策＝静默门；"任何时刻不拒连"的常驻代理延后（触发式）

> 术语速查：**渡口**＝本机代理，CC 全部 API 请求经它转上游；**排水**＝停机前等在途请求自然跑完；**换装**＝换程序文件（旧 exe 改名挪窝、新 exe 顶名）；**监督者**＝跑升级事务的程序（`ferryman update`）；**蜂群**＝各会话自带的"探活+拉起"钩子群。完整术语表见 `docs/20260929_升级链可靠性战役计划.md`。

2026-09-29 升级链拷问（底稿同上）定案。背景两层：① 当日上午两次自动升级全失败回滚（各约 2 分钟）、v0.2.6 靠手工换装上线——痛的主体是**可靠性病**（拉起不可验证/蜂群抢跑/旧监督者软等抢跑），已由 v0.2.6 硬门修复但**从未真正执行过一次升级**（跑升级的永远是旧 exe 的代码，修复随下一次升级才首跑）；② 就算链路全对，"停旧→换装→拉新"式升级仍有本质缺口：排水窗（≤180 秒）内**新请求被拒连**——在途流不断已由 ADR-0017 排水契约保证，但"不拒连"与"停旧后拉新"互斥。

决定两件：

1. **停顿对策＝静默门**（动手前等在途为零且近窗无新请求，把带载停机变成空载停机——空载实测全程 4 秒）。术语见 CONTEXT.md「升级窗口语义」。
2. **"任何时刻不拒连"（真无缝）不上常驻架构，触发式延后**：按"稳定后每 1-2 周一次、手动挑时机"的升级频率定价，为两周一次的 4 秒窗引入永久关键小进程不值。触发条件＝"随时升级不打招呼"成为真需求（如自动更新立项）。

## 弃选方向（为什么当时不造零停机）

- **听者移交**（旧进程把监听 socket 句柄传给新进程，两边同时收连）：零窗口，但句柄传不过 wscript/VBS 启动链、新旧共存要改唯一化逻辑、且依赖旧版配合——Windows+Go 下风险收益比最差。
- **旧进程反代移交**（排水期旧渡口把新连接转投新守护临时口）：同样要旧版里先有配合代码。两者同犯**自举悖论**：首次无缝升级永远晚一版。
- **缩窗**（升级时把排水上限压到 15-30 秒，长流被注入流内错误让 CC 重试）：最便宜，但牺牲"在途流不断"——与用户要的"无缝"自相矛盾。
- **常驻边缘代理**（下节）：唯一无自举悖论者（部署一次付一次窗，此后升级永不依赖旧行为）。**采纳其架构为延后方向，不立项**。

## 延后方向附录：edge 架构草图（上架时从这取，不重新想）

2026-09-29 讨论定型（用户提出"nginx+核心"两进程拆分，经磨准）：

- **拆的不是"中转 vs 记录逻辑"，是"端口所有权 vs 其他一切"**。记账、改写、闸门、快照、错误契约全留核心进程；edge 零状态零逻辑，唯一职责＝持有 15722、按代次转发、听令翻转。越哑越稳——它挂＝全场挂，必须配得上"冻结件"（基本不再改动的部件）。
- **翻转必须按请求（HTTP 层），不能按连接（TCP 字节层）**：CC 客户端 keep-alive 长连接会钉死在旧核上；edge 须理解 HTTP，同一条长连接上翻转前请求去旧核、翻转后去新核。
- **翻转权在监督者**：edge 不自作主张发现新核（不引健康检查/服务发现逻辑），由监督者事务经环回管理端点下令。
- **升级时序**：新核先起（不同代次私口）→ 探活 → edge 翻转 → 旧核后台排水退场。排水彻底离开关键路径；ADR-0017 排水机器在旧核原样复用。"不拒连＋在途不断"同时成立。静默门在此世界主要价值消失。
- **既定约束（用户已同意）**：接受热路径永久多一跳（本机亚毫秒级）；接受新增常驻小进程；接受 edge 自身升级时付 1-2 秒残余窗（改名让位同样适用）。看门/蜂群须扩一项探 15722。
- **控制面（15700）不进 edge**：MCP/闸门钩子几秒窗可忍（闸门钩子失败默认放行）。
- **隐性账**：edge 是此后每个排障会话都要多问一句的东西（"是 edge 还是核？"）。单人基建里这笔账正是延后决策的核心依据。

## Consequences

- 战役验收线用**在途零截断＋单次拒连窗 ≤10 秒**（静默门下换装+冷启的 ~4 秒窗是接受的），"零拒连"条款只对延后的无缝方向生效；验收线适用于静默门达成的升级，非交互硬切兜底路径不判负、窗口与截断如实记录（2026-09-29 复审停点拍板，D10）。
- 内存态（快照/判热时钟/等待窗/qwatch）跨升级**冷启不交接**：观察周证据（104 警告零漏拦）表明重启后冷态不伤正确性；此语义维持现状写死，不因无缝方向将来立项而自动升级为交接需求。
- ADR-0015 第 2 条部分修订（监督者事务拉起弃 wscript 层），见该 ADR 2026-09-29 补记。
