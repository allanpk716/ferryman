# 等待窗保温（机器等机器）授权实施：双泳道共用发送器，真发送统一以 Q14 为放行门槛

三泳道里"机器等机器"（等待窗口：主会话等在飞子代理）是唯一没有保温手段的一条——T48 停车窗解决的是"别误渡、别误拦"（豁免与摆渡推迟），不解决"子代理回来时缓存已死、主会话续跑全量重付"。实测痛点（Python 时期，2026-09-19 讨论锚点）：grill 类会话派 subagent 查事实动辄几十分钟，远超 GLM 实测 TTL 600s；03225787 会话等 subagent 期间被摆渡、回来被闸门拦下，被迫 /clear 后 grill 进度蒸发。闸门侧机器等机器豁免（Go 已落地）消掉"拦"，本决策消掉"贵"。

决定：授权实施等待窗心跳执行器——复用问询守望已落地的窗口/排程/新鲜度双验/熔断/记账骨架，双泳道（等待窗＋等答复窗）共用同一 HttpBeatSender 真身与同一道 Q14 放行门槛（BeatBuilder 逐字节 diff 全等＋3 臂实跳；方案 docs/20260918_Q14心跳保真度实验方案.md 已备，含 CC 别名保真雷：beat 必须发 CC 别名而非 jsonl 回显名）。治理约束全部沿用：opt-in、默认关（ADR-0004"不做无条件全局保活"红线不动）；全局同时至多 1 跳在途（多窗同开排队，遥测显示拖过期再升级为每会话 1 跳＋全局上限）；间隔与等待上限由策略计算器按价格表＋实测 TTL＋前缀大小闭式现算（公式单源，手动只能调低）；等待上限到达即停跳、放任过期，停车窗 1h 过期与摆渡恢复入队语义不动；miss 即停跳＋告警＋建议复测 TTL，不自改配置；逐跳入既有 beat 科目，未回归记无效保温单列。

后果：问询守望侧现接的 NoopSender 在 Q14 通过前保持不变（升 enforce 的硬闸语义与 ADR-0004 一致）；闲置定义与闸门语义一字不动（心跳不算写入，"判定只依据台账"根基不变）；「强续」前缀语义不动（明确否决"拦后再发即放行＋自动补待续 prompt"）；grill 技能本身不动（进度保全依赖豁免＋保温，不引入 checkpoint 文件）。（2026-09-19 补记：前缀源路线定为捕获重放，见 ADR-0007；Q14 段三当日执行通过——3/3 臂 HIT/HIT 真保温。）

## Considered Options

- **直接常开真发送，靠 miss 熔断兜底**：每跳 miss 按缓存写全价扣费，熔断前的几跳即净亏，且分不清"前缀不保真"与"服务端 TTL 漂移"两种 miss——否决，未验证命中率的常开等于闭眼烧钱。
- **只保温问询守望（机器等人），等待窗不做**：机器等机器才是最长等待（异步真身实测最长 34.8 分钟，停车盲区上限 1h），且 grill 的两类等待（等子代理查证、等用户逐条作答）各占一半痛点——否决。
- **停车窗续期（子代理转录有写入即续）＋到期前提醒**：只推迟误拦时点，不解决"回来全量重付"的成本主痛点——用户定向到心跳方案，否决，不与心跳叠加。
- **拦后再发即放行＋自动补待续 prompt（闸门 UX 软化）**：让被拦后继续零摩擦，属另一条根因路线；用户拍板"不动"，强续前缀语义照旧——否决。
