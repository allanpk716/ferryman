# 通知分级与降噪

2026-10-08 用户拍板：九类通知事件各配 `off | toast | both` 三值开关（配置组为 `[notify]` 节内的 `events` 内联表键，禁开独立 `[notify.events]` 子表头），未配置事件回落内置缺省表、生产 config 零写入即生效；滑落告警从"每次滑落推一条"改为**顺位级状态变化制**。验收口径＝手机 Pushover 端条数：日均 15~20 条 → 约 1~2 条。范围仅限 Ferryman 侧（claude-notify 插件共用 Pushover 凭据但相互独立，若砍完仍吵另开线）。实施随同日通知分级夜链各票。

## 问题（噪音实锤）

2026-10-01~08 生产账本重建：8 天约 120~160 条推送、日均 15~20 条，用户反馈过多。两大户占八成：

- **滑落告警**（`internal/daemon/worker.go` alertChainDegrade）：生产链 `chain = ["local", "zhipu-flash", "kimi-k3"]`，本地 4090 千问不稳，8 天 86 次 failed 尝试、每次滑落推一条且无节流，估 40~80 条（日均 5~10）。账本已逐次记账（handoff 科目 failed 行带 err 字段），推送无信息增量。
- **拦截通知**（gate.go NotifyBlock）：8 天 67 条（日均 8）。用户提交被拦时人必在场，对话区当场有反馈（ADR-0023 选择框），手机推送属事后噪音。

10-08 单日生产链车道 58 行重放：现网语义 12 条 → 状态变化制 2 条（14:02 滑至 zhipu-flash 一条＋17:29 滑至 kimi-k3 一条，17:36 恢复后无再滑落），塌缩 6:1。

## 决策

1. **事件级三值开关与缺省表**（用户两轮逐问确认）：每事件 `off`（全静默）/ `toast`（仅桌面）/ `both`（桌面＋手机双通道）。九事件缺省：`block = toast`；`chain_degrade = both`（仅状态变化首推，见下）；`chain_skeleton` / `breaker` / `upgrade` / `hard_cut` / `drift = both`；`tuning = off`；`tray_reply = toast`——即手机只收关键故障（骨架、熔断、升级、硬切、漂移、滑落首推），拦截反馈与托盘手动应答（检查更新、安全重启）仅桌面，调参静默。配置形状为 `[notify]` 节内 `events` 内联表键、禁独立 `[notify.events]` 子表头：设置视图的节级整写原语对带子表头的节保守拒写，子表头会使整个 `[notify]` 节在设置视图不可写；内联表键随节内容整写，两形态兼容。
2. **滑落告警改顺位级状态变化制**：状态＝最近一次成功到达的顺位（进程内存、不持久化、冷启动＝链首）。顺位下移推一条（文案含新顺位与原因；滑至链尾 kimi-k3——再失败即骨架——文案自然体现"最后一站"严重度，不新增独立事件类别）；同级持续失败不推；上移恢复静默重置、不推恢复（恢复不是故障，账本 fresh 行可查）。全链骨架 sync.Once（进程一次语义）与逐次记账（err 字段）不动。
3. **设置视图等值省略协议**（评审两轮、两家独立收敛的同一解法）：读面回落缺省值仅供展示；UI 提交体完整回传 `events` 对象；写入器规范化——与内置缺省表等值的键不落盘。两条往返测试钉死：不改 events 保存 → 盘上 events 相关字节不变；改一事件 → 盘上仅该键变化。

## T25 修订依据

block 双通道（Pushover＋Toast，priority=1 等细节被测试钉死）是 Python 版 1:1 平移的既定规格（notify 包头注释）。本篇把 block 缺省降为仅桌面 toast：ADR-0023 把被拦反馈搬进对话区选择框后，界面反馈已不依赖推送、人被拦时必在场，手机推送冗余。T25 的通道实现（SendPushover / SendToast、NotifyBlock 文案与 BuildTitle 标题降级链）不取代、原样保留。

## 取舍

- 重启不持久化：守护在降级状态下重启，同一次降级重启前后各推一条（不持久化状态的固有取舍，挂部署后观测）。
- 交替模式（本地间歇抖动：下移→恢复→再下移）每故障周期 1 条属设计预期；实测日均 ≥3 个独立故障周期时回用户决策是否加恢复抑制窗口。
- 显式配值恰等于当前缺省时被等值省略，该键随缺省演进——想把行为钉死只能配成非缺省值。

## 取代关系

修订 ADR-0024 时代"每次滑落推一条 Pushover/Toast 告警"的语义（该语义写于 CONTEXT.md「摆渡路由」词条降级告警句而非独立 ADR，本次随本篇落档，词条已同步）；不取代 T25 通道实现。既有开关与纪律不动：`[notify]` 总开关 `enabled = false` 仍全静默、pushover/toast 通道开关语义不动、通知仍是尽力而为旁路（异步发送、故障只吞、永不影响决策）。

## 后果

- 手机 Pushover 端从日均 15~20 条降到约 1~2 条（block 全走桌面＋滑落首推偶发）；桌面 Toast 条数基本不变。
- 缺省表随代码演进：用户显式配值恰等于旧缺省的键被等值省略，缺省更新后这些键行为随之变化。
- 部署后观测两件：重启后首滑落重推的频率、交替模式的独立故障周期数（日均 ≥3 回用户决策）。
- CONTEXT.md「摆渡路由」降级告警句改为状态变化制、新增「通知分级」词条（随本篇）；`config.example.toml` 注释同步归实施票。

## 修订（2026-10-09）：渡口形态漂移退出推送

drift 事件键原有两个发送方并轨共用：渡口形态漂移（`dock/drift.go`，票03 接线）与 `ferryman verify-dsh` 红灯（verify-dsh 战役收编）。本次把前者解绑——daemon 装配 `Options.Alert = nil`（`AlertViaNotify` 随之删除），形态漂移只落 serve 日志；drift 键转由 verify-dsh 红灯专用，缺省 `both` 不变。九事件封闭集合与配置形状不动。

依据：

- 渡口对未知形态原样放行（`headers.go` 白名单外只动 auth/beta 两处、请求体只改已知五件），形态漂移推送对用户零可执行动作；其取证价值在日志行（`drift.go` fire 落日志无条件），推送无信息增量。
- 登记表重启清零重建基线，重启密集期同一批无害参数（temperature / tool_choice / structured-outputs 等）反复"首见"重报——10-05~09 生产 serve 日志实测信噪比不可接受；未来用户为有用通知（block/升级等）开启 `[notify]` 即开始吃此类推送，解绑从根上断掉。
- verify-dsh 红灯保留推送：真故障（插件偏离已知良好）、可执行（查插件/回退已知良好版本），与形态漂移不同质。

CONTEXT.md「通知分级」「形态漂移告警」词条、`config.example.toml` 注释、widget 设置面 drift 行标签（0.2.8）随本修订同步。
