# "不保活"红线限缩为禁无条件全局保活：条件化会话级保温放行（问询守望）

DESIGN.md §9 设计红线"不保活"立项于守护进程初创期，针对的是**无条件全局 keepalive**——ferry 无差别续命所有会话：跨夜不可靠、持续烧钱、收益与代价无从对账，红线当时完全正确。但"拷问式"讨论技能（典型输出：一条 assistant 消息 5~10 个编号问题，要求逐条回答）引入了红线未预见的新痛点：用户组织长答案耗时 10~40 分钟，远超主力服务商实测 TTL（GLM ≈10 分钟）——缓存过期，答案提交时全量重付；闲置钟照走，第 25 分钟触发一次没人用交接的摆渡，第 35 分钟闸门把活人拦在门外。按字面执行红线，该场景无解；而红线真正要禁的形态（全局、无条件、无限续命）与解法（条件触发、单会话、有窗有上限）并无共性。

决定：红线限缩为"**不做无条件全局保活**"；条件化、会话级、短窗保温以问询守望（question watch）形态放行——紧判据检测问询潮（编号行须含问号或疑问词；实验定型：松判据 163/272 触发且 153 条误报全为状态汇报/评审报告/票台账，紧判据 10/272，判据按紧档定死不留给 observe 期再选），命中会话开等答复窗口，默认至多两跳（间隔 420s = 0.7×实测 TTL）把缓存可靠命中窗口从 ~10 分钟扩到 ~24 分钟，窗口随任何新写入立即关闭。等答复窗口内摆渡推迟但带硬死线（拦截阈值前 8 分钟强制入队、失败走既有骨架降级，"被拦 ⇒ 交接必已存在"不变量同水位成立），闸门语义一字不动；闲置定义一字不动（等答复窗口期间闲置照走——备选"暂停闲置钟 / 心跳计入台账活动"被否：动了"判定只依据台账最后写入"的根基，误报会让会话脱离闸门护栏）。治理约束：`[question_watch]` 独立配置节、三态 off/observe/enforce 默认关、切换永远人工拨且永不自动升级（连续 miss 自动降级 enforce→observe 是安全熔断，非升级路径）；Q14 心跳保真度实验（BeatBuilder 逐字节 diff 全等＋3 臂实跳）是升 enforce 的硬闸；CC 轨先行、Codex 轨缓行；隐私不变量沿用——判定只出 bool/计数，台账与账本永不落消息内容。

后果：§9 文案已同步改写（本 ADR 即其依据）；问询守望成为 Ferryman 第一个落地的心跳执行器（检测器 `ferryman/qwatch.py`、等答复窗口与台账 `ferryman/ledger.py`、调度 `ferryman/beat.py`+`ferryman/daemon.py`、事件与 `/stats` qwatch 节及 `POST /qwatch_stop`）——ADR-0003"心跳执行器 Python 中从未实现"的前提由本决策修订：先以 Python 落地 observe，迁 Go 时按 ADR-0003 路线原生重写、不保双实现。每跳费用逐条入既有 beat 科目，但账本数据不反推跳数（记归记、算归算）。已知取舍如实声明：默认档只保到命中后 ≈24 分钟，t∈(24,35) 死区提交者全量重付但有交接可看，>35 分钟提交者被拦且有交接引导开新会话——本功能不宣称"保到用户提交为止"。

## Considered Options

- **维持"不保活"红线原样**：拷问式长答场景必然全量重付＋活人被拦，痛点无解；且红线原文的打击面（一切保活）宽于其实际动机（全局 keepalive 的不可靠与烧钱）——否决。
- **全局心跳开关**：无差别续命所有会话，跨夜不可靠、持续烧钱，正是红线要禁的形态——否决（本 ADR 不为其开门，"不做无条件全局保活"仍红线）。
- **等答复期间暂停闲置钟 / 心跳计入台账活动**：可绕开摆渡误触发与第 35 分钟拦截，但动了"判定只依据台账"的根基，检测器误报会让会话长时间脱离闸门护栏——否决。
- **松判据（编号行全计）留 observe 期再选**：实验已证 60% 触发率且样例全为误报形态，observe 期再选只是推迟决定、白烧一周数据——否决，紧判据按实验定型。
