# GLM 缓存 TTL 实测与心跳保温可行性 —— 实验报告

- **日期**：2026-09-17
- **对象**：智谱 GLM Coding Plan（GLM-5.3）
- **背景**：[20260916_0853 技术调研](20260916_0853_Agent会话闲置缓存失效与自动交接_技术调研.md)确认智谱官方文档对缓存时效只有一句"缓存有合理的时效性，过期后会重新计算"，无任何数字。本报告用实验把它测出来。
- **工具**：`experiments/cache-ttl/`（可复用三轨套件：`probe_pi.py` / `probe_cc.py` / `probe_api.py`）
- **数据**：`experiments/zhipu-cache-ttl/results/`（pi 轨）+ `experiments/cache-ttl/results/`（CC 轨）

## 1. 测量环境

| 轨 | 链路 | 前缀规模 | 臂数 |
|---|---|---|---|
| pi 轨 | pi 0.74.2 → CC Switch 本地代理(127.0.0.1:15721) → GLM | ~17k token 独立资料/臂 | 53（多轮阶梯，含 11/12 分钟补测 ×4）+ 续命 1 |
| CC 轨 | claude -p（--session-id）→ 同一 CC Switch 代理 → GLM | ~41k token/臂（含 CC 系统提示 ~19k） | 8（4 档 ×2） |

方法：每臂一段全新确定性前缀，写入 → 干等 N 分钟 → resume 只探一次，读响应 usage 的缓存命中 token（pi/CC 轨读 cacheRead，判定阈值 ratio ≥0.85）。防污染设计（每臂独立前缀防探测续命、记 actual_gap、×3 重复）见套件 README。

## 2. 闲置 TTL 曲线（核心结果）

| 闲置时长 | pi 轨（17k 前缀） | CC 轨（41k 前缀） |
|---|---|---|
| 1–8 min | 12/12 全命中 | — |
| 10 min | 3/3 | 2/2 |
| **11 min** | **2/4（补测）** | — |
| **12 min** | **3/7（含补测）** | — |
| 14 min | 1/3 | 2/2 |
| 16 min | 0/3 | — |
| 18 min | 1/3 | — |
| 20 min | 1/3 | **2/2** |
| 30 min | 0/3 | **0/2** |
| 45–120 min | 0/9 | — |

**结论**：
1. **统一结论（与 Coding Agent 客户端无关）**：**闲置 ≤10 分钟确定性命中（两轨合计 17/17）；11 分钟起即有风险（11 分钟 2/4、12 分钟 3/7）；≥30 分钟确定性失效**。风险区从 11 分钟一直延伸到 30 分钟前，区内命中率不稳定（受服务端驱逐/负载影响，不是定时坏死）。任何客户端（pi / Claude Code / 其他）走 GLM 编码套餐都适用这三个数；工程规划统一按 10 分钟安全线，心跳间隔 8 分钟（0.8×10）。
2. 两轨在风险区的数字差异（pi 轨 8/23 vs CC 轨 6/6）**不代表客户端影响 TTL**——缓存按内容前缀组织、与客户端身份无关（见下条跨会话证据）；差异更可能来自前缀规模（17k vs 41k）、时段负载与样本量（CC 轨每档仅 ×2）。若需分辨，需同槽位加大重复数复测。
3. **命中二值**：全程无部分命中（ratio 要么 ~1.00 要么 0.00），前缀 KV 缓存整存整取。
4. **跨会话前缀共享**：多臂共享相同系统提示头时互相蹭到命中（pi 轨 320 token、CC 轨 19136 token 规模）——缓存按内容前缀组织，不按会话/客户端隔离。

## 3. 续命语义（心跳可行性）

单前缀每 9 分钟 resume 一次 ×6：

```
t+9.1  HIT   t+18.1  HIT   t+27.1  HIT
t+36.1 HIT   t+45.0  HIT   t+54.1  HIT   （6/6，cacheRead 始终 ≈17k 满值）
```

**结论：命中会刷新计时。** 闲置最多活 20–30 分钟的缓存被 9 分钟间隔的廉价命中摸着活满 54 分钟。心跳保温在 GLM 编码套餐上成立。

## 4. 心跳成本模型（可计算，勿玄学）

输入四个量：输入价 `P_in`、缓存命中价 `P_cache`、输出价 `P_out`（GLM-5.3 编码套餐积分系数：6.9 / 1.7 / 24 每万 token）、实测可靠 TTL `T`（本报告 §2）。

| 量 | 公式 | GLM 代入（S=150k 前缀） |
|---|---|---|
| 心跳间隔 τ | `0.8 × T` | 8 min |
| 单次心跳成本 | `S×P_cache + ~300×P_out` | ≈26 积分 |
| 放任过期代价 | `S×P_in` | ≈103.5 积分 |
| 心跳划算的等待上限 | `τ × S×(P_in−P_cache) / 单次成本` | **~25–28 分钟** |

**分档决策矩阵（多 subagent 编排）**：

| 主控等待时长 | 策略 |
|---|---|
| ≤8 min | 什么都不做（缓存必活） |
| 8–28 min | 心跳保温（每 ~8 min 一次体外重放） |
| ≥28 min | 放任过期付一次重算；若前缀很大，等待前先 compact 把重算代价缩小 |

心跳的正确实现载体是**体外重放**（守护进程重构前缀直打本地代理、不写会话文件、用户聊天界面无感），而非驱动会话 resume（会污染历史+并发风险）。触发必须事件驱动、opt-in、默认关闭，且每次心跳的 cacheRead 即线上 TTL 遥测——突然 miss 要告警并自适应。费用须逐条记账（含价格表版本化、预测 vs 实收对账）。**注：以上为设计参考，未经用户明确要求不实施。**

## 5. 对两个编排问题的回答

**Q：主控开一群 subagent 做调研，回来后缓存是不是已失效、汇总要重新计费？**
基本正确。等待 ≥30 分钟缓存必死；主控恢复后第一发按输入系数全量计费（150k 前缀 ≈103.5 积分，比缓存价贵 ~4 倍）+ prefill 延迟。修正一处：不是"重新命中缓存要花钱"——重写缓存不单独计费（cacheWrite 计费观测为 0），代价是那一发从 1.7 回到 6.9 系数的一次性差额，此后恢复缓存价。11 分钟起就是风险区（补测 11 分钟 2/4），恰好落在心跳划算区（§4）。

**Q：等待触发超时→提醒用户 clear→加载 handoff，这个思路有问题吗？**
三个问题：① 时序错——compact 的最佳时机是派发 subagent **之前**（把将要死的前缀提前缩小），超时后 clear 是同一操作发生在最打断用户的时刻；② 把省积分的成本决策推给用户手动执行文件操作，体验差；③ 短中等待下强制交接可能更贵——交接文档生成（输出价）+ 新会话重建（新前缀全量输入价）可能超过一次 103.5 积分的重算。handoff 应是"长等待 × 大前缀 × 任务可断点"场景的选项，不是默认。§4 的分档矩阵给出完整替代方案。

## 6. 复测触发条件

- GLM 大版本升级（5.3 → 下一代）或编码端点变更
- 心跳上线后首次实收 miss（自适应告警）
- 常规：季度性跑一轮套件粗阶梯交叉验证（LRU 负载敏感，本报告为 2026-09-17 午后时段结果）
