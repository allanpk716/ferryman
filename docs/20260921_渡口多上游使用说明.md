# 渡口多上游使用说明（三家直连 · 一条命令换上游 · DeepSeek 边界）

- 日期：2026-09-21（票 04 产出；ADR-0011 渡口多上游直连的使用面，与 `docs/20260919_渡口切换_runbook.md` 同水位）
- 术语：**渡口 / 渡口上游 / 摆渡供应商 / 换上游** —— 见 `CONTEXT.md`。本说明只管渡口上游（Anthropic 协议，`[dock.upstreams.*]`）；摆渡供应商表（`[providers.*]`，OpenAI 协议）完全分立、互不联动。
- 事实源：端点与模型档位转录自 `internal/config/dock_migrate.go`（三条预置）与 `config.example.toml`；DeepSeek 边界为官方已知限制（spec F2 收敛口径），与 `ferryman doctor` 的 `dock_deepseek_boundary` 行同文。
- 红线：api_key 只写本机 `~/ferryman/config.toml`，永不入 git/日志/账本（T39）。

命令约定：代码块内一律 ASCII 命令行，可逐字复制；`<...>` 为占位符（复制时替换）；中文只在说明文字里，不进命令行。

## 0. 三家端点与模型档位

条目名即 `[dock.upstreams.<名>]` 的 TOML 键（`ferryman upstream use` 也用它）。档位键 = CC 侧模型别名（opus/sonnet/haiku/未知名）映射到的上游原生模型名；`default` 必填（未知名兜底）。

| 条目名 | 端点（base_url） | default | opus | sonnet | haiku | balance_url |
|---|---|---|---|---|---|---|
| `智谱` | `https://open.bigmodel.cn/api/anthropic` | glm-5.3 | glm-5.3 | glm-5.3 | glm-5.3-flash | `https://open.bigmodel.cn/api/user/balance` |
| `kimi` | `https://api.kimi.com/coding/` | kimi-for-coding | k3 | kimi-for-coding | k3-256k | （不配不显示） |
| `deepseek` | `https://api.deepseek.com/anthropic` | deepseek-flash | deepseek-v4-pro | deepseek-flash | deepseek-flash | （不配不显示） |

- **kimi 不用 `kimi-for-coding-highspeed`**：其"强制 thinking"属性未核实（F5），核实前不预置。
- kimi 的 key 在 Kimi Code 控制台建（Coding Plan），与 API 开放平台的 key 不通用（以你手中实际 key 验证，D13 备注）。
- 模型拼写以各家官方文档为准（2026-09-21 查证预填；模型名换代快，用户验收终值）。
- 回退条目 `cc-switch`（`http://127.0.0.1:15721`）不在上表：它是旧单值配置迁移出的本地中转通道，指向本地中转地址（回环＋15721/15722/15723 任一端口）时守卫**强制透传**（防双重改写）——该通道永远是纯透传，出站鉴权由 cc-switch 自己做。

## 1. key 手编填法

编辑 `~/ferryman/config.toml`，在对应条目下填 `api_key`，**重启守护生效（无热加载）**：

```toml
[dock.upstreams."智谱"]
api_key = "<你的智谱 key>"
```

重启三步：停（托盘「退出」或关 start-daemon 窗口）→ 改配置 → 起（`~/ferryman/start-daemon.cmd`）；看门在位时停进程 5 分钟内会被拉活——改配置窗口期先按 runbook §4 停看门。

`ferryman doctor` 会对每条缺 key 的非本地条目出一行提示「渡口上游 <名> 未配置（手编 config 填 api_key）」——提示不判失败（未激活预置属正常状态）；本地中转条目（cc-switch）不出站鉴权，不需要 key、也不提示。

## 2. 换上游与回退（一条命令）

```bat
ferryman upstream list
ferryman upstream use 智谱
ferryman upstream use cc-switch
```

- `upstream list`：全部条目＋active 标注＋base_url/model_map 概要＋可用状态（缺 key 显示"未配置，需手编 config 填 api_key"）＋密钥脱敏。
- `upstream use <名>`：条目不存在或缺 api_key → 拒绝并如实报错；通过 → 校验配置 → 原子写 config → 自动重启守护 → 健康检查（几秒生效）。
- **换上游即冷启动，代价须知**：在途请求允许中断（命令会提示）；旧会话的内存缓存快照随重启清空——旧会话按冷启动全量重付；心跳自动跟随新上游；台账由启动扫描重建；交接库不受影响。纯手动，无故障转移。
- 切换后守护没起来：命令如实报「配置已切换为 <名>，守护未起来」，手动拉起（`~/ferryman/start-daemon.cmd` 或 `ferryman watchdog`）或回退（`ferryman upstream use cc-switch`）；不自动回滚、不自动重试。
- **回退一条命令**：`ferryman upstream use cc-switch`（或手编 `[dock].active = "cc-switch"` ＋ 重启）＝ 回到本地中转透传态，任何时刻可走。

## 3. DeepSeek 官方已知边界（与 doctor 输出同文）

激活 deepseek 条目时，`ferryman doctor` 会输出以下提示行（上游侧限制，非本实现故障）：

- **不支持的消息类型**：`document`、`search_result`、`redacted_thinking`、`mcp_tool_use`、`mcp_tool_result`
- **被忽略的语义**：`tool_result.is_error`、`tool_choice.disable_parallel_tool_use`、`thinking.budget_tokens`
- **遇不支持负载**：渡口如实透传上游错误（不做协议转换）
- **处置**：人手换上游——`ferryman upstream use <其他条目>`

## 4. 升级迁移行为（旧单值配置 → 上游表）

- 升级后**首次启动守护**时自动迁移：旧 `[dock]` 单值（upstream_base_url/api_key/model_map 等）迁出名为 `cc-switch` 的回退条目并**保持 active**——链路仍经本地中转（127.0.0.1:15721），行为零变化；同时生成智谱/kimi/deepseek 三条未激活预置（api_key 留空占位，填 key 即用）。
- 迁移幂等：`[dock.upstreams]` 表已存在即跳过；迁移失败守护按旧单值兜底行为继续跑并告警——`ferryman doctor` 的「渡口上游」行会提示旧单值未迁移，并指向异形排查（检查 config `[dock]` 节是否含空值键等）。
- **行为变化提示**：改写自本版起隐含开启（无 rewrite_enabled 开关）。迁移出的 cc-switch 条目若上游非本地（旧直连形态），升级前 `rewrite_enabled = false` 的纯透传不再保留——doctor 会出一行「改写已隐含开启」的行为变化提示；本地回退通道不受影响（守卫强制透传，行为不变）。
