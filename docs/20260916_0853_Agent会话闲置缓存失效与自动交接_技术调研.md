# Agent 会话闲置缓存失效与自动交接 —— 技术调研

> 调研日期：2026-09-16
> 场景：用 Claude Code / Codex CLI 长会话工作，闲置后 prompt cache（提示词缓存）失效，恢复会话要为全部历史上下文重新付费/扣额度。想要一个本地软件：自动监控会话 → 闲置后自动总结成交接 MD → 提醒 → 次日开新会话低成本续接。
> 结论先行：**方案可行，且两头（总结、续接）都能自动化；本机数据基础完备；不需要抢缓存过期前的时间窗。** 另：社区调研确认"闲置触发+自动总结+外部提醒"三合一**没有任何现成品**（唯一跑通过的 dthinkr/auto-compactor 已删库，只在 issue 评论区留下 842K→13.5K token 的实测数据），属于真空位——各零件轮子充足，组装即可。
> **第二轮核实（同日）：强制拦截层可行、无疑问遗留**——用户点名的四家（Claude Code / Codex / Pi / DeepSeek Harness）全部具备"提交 prompt 前硬阻断"的官方原生能力（详见 6.5 节）；无钩子工具可用代理层启发式兜底（LiteLLM 现成能力，非主路径）。

## 1. 问题本质（大白话版）

- **prompt cache 是什么**：模型服务商把你上一轮请求的上下文（系统提示+工具定义+对话历史）算过的部分存起来，下一轮完全相同的前缀直接复用，只收 10% 的钱（Anthropic/OpenAI 口径）。
- **怎么失效**：缓存有保质期（TTL）。Anthropic 默认 **5 分钟**（订阅套餐内主对话默认 1 小时）；OpenAI GPT-5.6+ 默认 **30 分钟**、旧模型约 5-10 分钟；智谱 GLM 服务端自动管理、时长不公开（**2026-09-17 实测：≤10 分钟必活、11 分钟起有风险、≥30 分钟必死、命中刷新计时**，见 §2.4 补齐块）。每次命中会免费刷新保质期——但只要你人离开了超过保质期，缓存就死了。
- **失效了怎么疼**：下次再发消息，整个历史上下文（可能 10 万 token+）要**全价重新算一遍**。按量计费路线=真金白银；订阅制路线（GLM Coding Plan / ChatGPT 订阅）=额度消耗瞬间放大 + 响应变慢。
- **注意**：这不是 bug，是所有厂商的默认行为。Anthropic 官方文档明确承认"stepping away 后回来第一轮会明显变慢变贵"。

**本机实际路由（2026-09-16 确认）**：Claude Code 走 CC Switch 代理（127.0.0.1:15721），主力模型实际映射 GLM-5.3（智谱 Coding Plan 订阅）；Codex CLI 0.153.0 走 ChatGPT 订阅。即日常痛的是**额度**，切到 API key 路线时痛的才是**钱**。

## 2. 三家缓存机制与计费事实（官方一手来源）

### 2.1 Anthropic（Claude）

来源：https://platform.claude.com/docs/en/build-with-claude/prompt-caching 、https://platform.claude.com/docs/en/about-claude/pricing （查证 2026-09-16）

| 项目 | 事实 |
|---|---|
| 默认 TTL | **5 分钟**，从发起请求起算；命中免费刷新 |
| 1 小时 TTL | 存在（`cache_control: {type:"ephemeral", ttl:"1h"}`），已 GA，现行文档不再要求 beta header |
| 计费倍率 | 5m 写入 **1.25×**、1h 写入 **2×**、命中 **0.1×**（新旗舰 Fable 5.1/Mythos 5.1 命中 0.025×） |
| 当前价格 | Opus 4.8：输入 $5 / 命中 $0.50 / 输出 $25（每百万 token）；Sonnet 4.6：$3/$0.30/$15；Haiku 4.5：$1/$0.10/$5 |
| 命中条件 | **前缀 100% 一致**（tools→system→messages 顺序，到 cache_control 标记为止）；任一处改动，其后全部失效 |
| 最小可缓存 | 按模型分档：Opus 4.8 = 1024；Haiku 4.5 = 4096；低于阈值静默不缓存 |
| 隔离粒度 | organization → workspace；**同 workspace 内外部脚本复用缓存明确允许**（只要前缀完全一致） |

### 2.2 Claude Code（CLI 层，官方文档 code.claude.com）

来源：https://code.claude.com/docs/en/prompt-caching （查证 2026-09-16）

- Claude Code 自动管理缓存，**主对话与 subagent/workflow/compact 等分两个桶**：
  - 主对话：Claude 订阅且额度内默认 **1h**；**API key / 自定义网关（含 CC Switch 这类代理）默认 5m**；
  - 其余（subagent、compact、会话标题等）：默认 **5m**。
- **TTL 可配置**（需 **v2.1.242+**，本机 2.1.232 暂无）：settings `promptCacheTtl` / `subagentPromptCacheTtl`，或 env `CLAUDE_CODE_PROMPT_CACHE_TTL`，取值 `5m`/`1h`。走自定义网关需网关原样转发 `anthropic-beta` 头（CC Switch 是否转发需实测）。
- **冷缓存下 /compact 本身也是全量重付一次**（官方原话"This is why /compact costs the most when you resume an old session"）。
- 验证实际 TTL：`claude -p "hello" --output-format json` 看 `usage.cache_creation` 里 `ephemeral_1h/5m_input_tokens`。
- 官方原生"恢复大.session"机制：Pro/Max 订阅下恢复**闲置>1h 且>100K token** 的会话时自动弹窗三选一（Resume from summary=当场 compact 一次 / 全量恢复 / 不再询问）。订阅网关路线（如 GLM）能否触发未验证。

### 2.3 OpenAI / Codex

来源：https://developers.openai.com/api/docs/guides/prompt-caching 、https://developers.openai.com/api/docs/pricing 、https://help.openai.com/en/articles/20001106-codex-rate-card （查证 2026-09-16）

| 项目 | 事实 |
|---|---|
| 触发方式 | **自动**，无需显式标记；GPT-5.6+ 可选 implicit/explicit |
| TTL | GPT-5.6+：`prompt_cache_options.ttl`，唯一取值 **30m**（默认），复用刷新；旧模型（含 gpt-5.3-codex）：约 **5-10 分钟不活动，最长 1 小时**，不保证 |
| 计费 | 命中 = input 价的 **10%**；GPT-5.6+ 写入收 1.25×，旧模型写入不额外收费 |
| 价格（API） | gpt-5.3-codex：$1.75 / $0.175 / $14；gpt-5/5.1：$1.25 / $0.125 / $10 |
| 命中保证 | **尽力而为**（与 Anthropic 的确定性前缀匹配不同）——路由 key 只影响路由不保证命中 |
| 最小可缓存 | GPT-5.6+ = 1024 token |
| **订阅模式** | 2026-04-02 起 Codex 按 token 折算 credits 计费，rate card 单列 cached input（如 GPT-5.6 Sol：125/12.5/750 credits）——**缓存失效在订阅下同样伤额度**，只是结算单位是 credits 不是美元 |

### 2.4 智谱 GLM（本机主力）

来源：https://docs.bigmodel.cn/cn/guide/capabilities/cache 、https://bigmodel.cn/pricing （查证 2026-09-16）

- 缓存**服务端自动**，基于内容相似度触发，TTL 官方不公开（"合理的时效性"），不可配置。**→ 2026-09-17 已实测补齐，见下方补齐块。**
- API 按量价：GLM-5.3 输入 8 元/M、**缓存命中 2 元/M**（75 折，不是 90 折）、输出 28 元/M；GLM-5.3-Flash 输入 0.8 元/M、命中 0.23 元/M。
- **关键**：官方明文"上下文缓存差异化计费仅适用于标准 API 计费，**不包括 GLM Coding Plan 套餐**"——订阅制下缓存死活不直接改变账单，改变的是额度消耗与速度。

**2026-09-17 实测补齐**（61 臂阶梯 + 1 续命序列，pi/CC 双轨均经 CC Switch 真实链路；详见 [20260917_1630 实验报告](20260917_1630_GLM缓存TTL实测与心跳保温可行性_实验报告.md)）：

- **闲置 ≤10 分钟确定性命中（17/17）；11 分钟起即有风险（11min 2/4、12min 3/7）；≥30 分钟确定性失效**。与客户端无关——缓存按内容前缀组织、跨会话共享（实测不同会话互蹭系统提示头命中，最大 19136 token）。
- **命中会刷新计时**：9 分钟间隔连摸 6 次，缓存活满 54 分钟全程满命中——**心跳保温在 GLM 编码套餐上成立**。
- 命中二值（整存整取，无部分命中）。心跳成本模型（150k 前缀）：26 积分/次 vs 放任过期重算 103.5 积分/次，**心跳划算的等待区间 ≈ 8–28 分钟，间隔 8 分钟**。
- 数据与复测：原始数据在 `experiments/zhipu-cache-ttl/results/` 与 `experiments/cache-ttl/results/`；通用三轨复测套件在 `experiments/cache-ttl/`（可测任意服务商/模型）。

## 4. 官方给的原生积木（自建方案直接可用）

### Claude Code 侧
- **SessionStart hook**（matcher: startup/resume/clear/compact/fork）：可经 stdout 或 `hookSpecificOutput.additionalContext` **注入上下文**——官方教程标题就叫"Re-inject context after compaction"。⇒ **"新会话/clear 后自动带上一份交接 MD"官方支持**。
- **SessionEnd hook**（matcher: clear/resume/logout/prompt_input_exit/other）：拿到 `transcript_path`，官方点名用法就是归档 transcript。
- **headless 续接**：`claude -p --resume <session-id> "..."` 官方支持（`--output-format json` 带 session_id/成本/usage）；**`-p` 下执行 `/compact` 无官方支持说明**，官方给的替代路径就是用普通 prompt 让它总结。
- `/export [filename]` 导出人读版会话；`/compact [instructions]` 手动压缩（摘要写回会话内）；auto-compact 阈值可调（`autoCompactWindow`）。
- statusline 输入 JSON 含 `cost` 与 `prompt_cache`（warm/cold、TTL、命中率——**v2.1.251+**）。
- 官方**没有**"闲置 N 分钟自动总结"的定时器功能。

### Codex 侧（比预期好）
- **Codex 有完整 hooks 机制**（`~/.codex/hooks.json` 或 config.toml `[hooks]`，需 `features.hooks = true`）：事件含 **SessionStart（matcher: startup|resume，source: compact）/ SessionEnd / PreCompact / PostCompact / Stop** 等，支持 `additionalContext` 注入与 Windows 专用命令覆盖。⇒ **续接自动化两边都能做**。
- `codex exec`（headless）+ `codex exec resume <SESSION_ID>`；`--json` 事件流；`/compact` 斜杠命令存在，自动压缩阈值 `model_auto_compact_token_limit` 可配。
- `notify` 配置项：给外部命令推 JSON 通知（仅用户级 config.toml）。

## 5. 社区现成轮子（prior art）与空白点

**痛点普遍性（官方承认）**：Claude Code 团队成员 bcherny 两次在 HN 公开确认"闲置>1小时=全额 cache miss，极端 900K token 会吃掉大块额度"（https://news.ycombinator.com/item?id=47880089 、47740541）。GitHub anthropics/claude-code 上至少 6 个 open issue 请求同一功能（#66115/#44789/#45040/#51218/#77266/#71254），其中 #66115 评论区给出关键账：**真实会话 input 的约 95% 走 cache_read（0.1×），TTL 过期后这 95% 要按写价 1.25× 重建——差价约 12.5 倍**；#51218 实测 912K 会话闲置 45 分钟后一条 200 token 消息吃掉 5 小时额度的 ~20%。Anthropic 工程师的缓存指南也明确建议："空闲超过一小时，与其恢复变凉的旧会话，不如做一次清晰的交接（session handoff）再开新会话"——**社区主流省法=手动 handoff，正是本方案要自动化的那一步**。反编译侧证：CC 内部已有 Time-based Microcompact 原型（60 分钟阈值，默认关、远程实验 flag）。

### 5.1 三条已被社区趟明的"死路"（避坑）

1. **hooks 没有 idle/timer 事件**；**CronCreate 不能调 CLI 命令**；**无外部进程能向运行中会话注入 /compact**（#44789/#45040/#77266 确认）。
2. 官方曾一次更新让 cron 计划任务里的 "/compact" 静默失效（#75837）——依赖 CLI 内部通道的方案有被官方更新打断的前科。
3. **保活路线（keep-alive）跨夜不可靠**：CPA 插件实测"Claude 账号会在一天某个时刻（如早 8 点）把缓存全清，想免费跨天不太行"（https://linux.do/t/topic/2901083 ）——保活只适合"离开 1 小时内"场景，隔夜正解就是总结交接。

### 5.2 三条已验证的技术通道（外部触发压缩/总结）

| 通道 | 代表 | 说明 |
|---|---|---|
| tmux send-keys 注入 | sure-scale/claude-code-auto-compact (4★)、nutoanan/claude-tmux-compact | 从后台向终端发 /compact，不抢焦点；受 CLI 行为变更风险 |
| headless fork 回合 | Efs-O/CacheWarden (VS Code 扩展)、dthinkr/auto-compactor（**已删库**，见 #71254 评论区） | `claude -p --resume` 派生会话干活；dthinkr 实测闲置 50-58 分钟窗口触发 /compact，**842,223→13,555 token**，耗时 3m16s 移到闲置期 |
| 直接改写 JSONL | Ruya-AI/cozempic (412★) | 阈值驱动对 jsonl 剪枝（剥旧工具输出/thinking），不调 API；工程最重、格式维护成本最高 |

### 5.3 各环节最佳现成件

| 环节 | 最佳现成件 | 与本方案的关系 |
|---|---|---|
| 会话结束自动总结 md | **vulcanshen/clerk**（38★，Go，GPL-3.0）：SessionEnd hook 触发 API 总结→`~/.clerk/summary/日期/slug.md`+倒排索引，支持任意 OpenAI 兼容端点 | 结构几乎就是"零件4+5"的雏形，但**无闲置检测**（纯 hook 驱动，挂着不动不触发）、无通知 |

| 成本仪表盘 | ccseva、cccost-dashboard、cc-lens 等 10+ | 全部"事后看账"，无一识别"缓存失效事件"并联动动作 |
| Codex 侧 | openai/euphony（官方 session 查看器）、cdxresume、codex-history-list | Codex 侧"闲置自动总结"完全空白 |

### 5.4 空白点结论

"**闲置触发器 + 总结 + 外部提醒**"三合一无人做成；会话浏览器（15+）、handoff skill（15+）、保活（4+）各自饱和。本方案 = 把 clerk 的总结落盘 + dthinkr 的闲置窗口思路 + 自建外部提醒组合起来，且总结通道选用更安全的"独立 API 调用"（见 6.2），不碰 CLI 内部机制。

## 6. 方案设计（讨论稿：五零件架构）

```
[1] 监控器(常驻) → [2] 会话登记本 → [3] 闲置判定(阈值可配)
→ [4] 总结执行器(模型可配) → [5] 交接MD库 + 提醒 + 查看界面
```

1. **监控器**：Windows 常驻进程，轮询两个 sessions 目录的文件 mtime（规模仅数百文件，轮询足够；将来要快可上 ReadDirectoryChangesW/USN——文件搜索工具调研已有积累）。
2. **会话登记本**：解析 jsonl 提取 ai-title/项目路径/最后 timestamp/上下文 token 数（来自 usage 行）/模型；防御式解析。
3. **闲置判定**：`闲置时长 > 阈值(默认 2h?)` **且** `上下文 > 门槛(默认 20-30K token)` 才触发——小会话不值得管。会话"复活"（用户回来了）要能取消/重算状态。
4. **总结执行器**：**独立 API 调用**（不驱动原会话、不污染 transcript）：把 jsonl 里 user/assistant 文本抽出（大工具输出截断/跳过，控制输入上限），发给配置的总结模型（默认建议 GLM-5.3-Flash，10 万 token 输入 ≈ 8 分钱；可选本地 4090 Qwen3.8-27B 零成本，或主力模型换质量）。走 CC Switch 或直连智谱均可配。
   > 通道安全性说明：社区趟明的三条通道（tmux 注入/headless fork/直接改 jsonl）都要碰 CLI 内部机制，各有官方更新打断的前科；本方案选的"独立 API 调用"是第四条路——**只读 jsonl 当原料，完全不碰运行中的 CLI**，风险最低，代价是放弃了"趁缓存温热时压缩"的省钱优化（对订阅制路线本来也不值钱）。
5. **交接 MD 库 + 提醒**：本软件管理目录，命名带日期时间+项目+会话标题；通知复用 claude-notify（Pushover + Windows Toast 已就绪）；界面 v0=托盘+通知+文件夹，v1=会话列表窗口（状态：活跃/闲置/已总结/已过期，按钮：打开MD/复制续接指令）。
6. **续接（第二天）**：
   - CC：SessionStart(resume/clear) hook 自动注入该项目最新交接 MD；
   - Codex：hooks 的 SessionStart 同理（新发现，能力与 CC 对齐）；
   - 兜底：手动把 MD 路径丢进新会话。

### 设计上明确不做的事
- 不抢 5 分钟缓存过期窗（只在按量 API 路线有意义，复杂度暴增，收益边际）；
- 不做保活（keep-alive）：CPA 插件实测服务端每天定点强制清缓存，跨夜不可靠；保活还持续花小钱，与"断舍离"方向相反；
- 不嵌进 Orca、不动 Orca hooks（独立小工具，避免和监军体系耦合）；
- 不做实时流式解析（轮询 mtime 足够）；
- 不碰运行中会话（不注入 /compact、不改 jsonl）——只读+外置总结，规避官方更新风险（前科见 #75837）。

## 6.5 强制拦截层（第二轮讨论新增，2026-09-16，待三路核实补全）

用户提出的升级：不做"只提醒"，要做**门闸**——每个 Agent 的会话在用户发消息前先过一道钩子，问询守望者软件"此会话超时了吗"，超时则**阻断本次提交**并告知去哪拿交接 MD、要求 /clear 后新会话续接。这把系统从"建议型"升级为"强制型"，防的是"第二天偷懒直接在旧会话打字→全量重读"这一步。

设计草案（待核实）：
```
用户在旧会话输入 → [各 Agent 的"提交前钩子"] → 问本地守望者(HTTP/文件)
   ├─ 未超时 → 放行（正常发送）
   ├─ 超时且有交接MD → 阻断 + 提示"去 X.md，/clear 后重开"
   └─ 超时且无MD（还没来得及总结）→ ？（放行+警告 or 阻断，待定）
用户 /clear / 新开会话 → SessionStart 钩子自动注入该项目最新交接 MD
```
待核实的关键事实（三路调研进行中）：① CC UserPromptSubmit 是否支持阻断（exit 2）；② Codex hooks 的 UserPromptSubmit 阻断语义；③ Pi/omp 有无等价拦截点；④ DeepSeek 官方工具现状；⑤ 无钩子工具的兜底（代理层拦截）可行性。

### 6.5.1 CC 侧核实结果（2026-09-16，官方文档确认）✅ 全部可行

来源：https://code.claude.com/docs/en/hooks 、/hooks-guide

1. **拦截点 = UserPromptSubmit hook，官方原生支持阻断**：`exit 2` 或 JSON `{"decision":"block","reason":"...","suppressOriginalPrompt":true}`。官方原文："Blocks prompt processing and erases the prompt"——被拦的那句话**不会进上下文、不会发给模型**；`reason` 直接显示给用户（不是给 Claude）。这是"门闸"语义，正是所需。
2. **触发范围无豁免**：交互 TUI、headless `claude -p`、`--resume`/`--continue` 恢复的会话都会触发（官方："fires the same hook events wherever it runs"）。
3. **stdin 字段齐全**：`session_id`、`transcript_path`、`cwd`、`prompt`（用户刚提交的原文）等。
4. **"问询我的软件"有原生通道**：CC 支持 `type:"http"` 的 hook——把事件 JSON 直接 POST 到本机守护进程（如 `http://localhost:PORT/hooks/user-prompt-submit`），响应体就是决策 JSON（阻断也靠 2xx+JSON body）。不需要写解析 stdin 的脚本。（旧版本无 http 类型时退化为 command hook + curl。）
5. **超时与故障语义（重要坑）**：UserPromptSubmit 默认超时 30s；**超时=放行**（fail-open，官方原文"prompt still reaches Claude"）。要"问不到=拦截"必须脚本内自设短超时（1-3s）+ 主动 exit 2。守护进程挂了时闸门失效——需接受或显式处理。
6. **不拦截时也能注入**：UserPromptSubmit 属于 4 个"stdout 可注入上下文"的事件之一（另三个：UserPromptExpansion/SessionStart/PostModelSwitch）；JSON 方式用 `hookSpecificOutput.additionalContext`（**放顶层会被静默忽略**——官方点名的坑）。
7. **SessionStart 不能阻断**（exit 2 只显示错误、会话照常启动），只能注入上下文——所以"拦截"只能发生在用户发消息那一刻。**但 v2.1.251+ 的 SessionStart(resume) 自带 `seconds_since_last_response` 字段**（本机 2.1.232 无此字段，靠守望者自己记账替代）。
8. **transcript 落盘有延迟**（官方："written asynchronously and may lag"）——钩子触发时新 prompt 可能还没写入 jsonl。恰好利好：守望者外部记的"最后写入时间"天然就是上一轮的时间，闲置间隔判断直接可用；不要在钩子里解析 jsonl。
9. **hooks 不能替用户执行 /clear**（官方明令"They can't trigger `/` commands"）——提示文案里让用户手敲 /clear，随后 SessionStart(clear) hook 自动注入交接 MD，闭环成立。
10. 对照：Stop 的 exit 2 语义是"不许停、继续干"（喂给 Claude）；PreCompact 可阻断压缩。方向各不相同，别用错事件。

CC 侧落地配方：
```
UserPromptSubmit (command 或 http hook, timeout 2-3s)
  → 问守望者：session_id 距上次真实活动多久？有交接MD吗？
  → 未超时：放行（可选顺带注入一行"缓存还温"状态）
  → 超时+有MD：{"decision":"block","reason":"此会话已闲置Xh，缓存已失效。交接文档: <路径>。请 /clear 后新开会话（会自动加载交接）。"}
  → 超时+无MD：放行+警告 or 阻断（产品决策，默认建议放行+警告）
/clear 之后 SessionStart(clear/startup) hook 注入该项目最新交接 MD
```

### 6.5.2 Codex 侧核实结果（2026-09-16，官方文档+源码确认）✅ 可行，有一个部署大坑

来源：https://learn.chatgpt.com/codex/hooks + openai/codex 源码（codex-rs/core/src/session/turn.rs 等）

1. **UserPromptSubmit 支持阻断，两条路**：JSON `{"decision":"block","reason":"..."}`（**reason 必须非空，否则记为 Failed 且不阻断**）或 `exit 2` + stderr。源码确认：被拦的 prompt **不写 rollout、不发模型请求（0 token）**（issue #32491 实测"turn completes with zero input/output tokens"）。
2. **拦截语义与 CC 高度同构**：同一套"问询脚本"几乎可以两家复用（都认 exit 2 + stderr）。
3. **SessionStart 注入**：matcher `startup|resume|clear|compact`；stdout 纯文本或 `hookSpecificOutput.additionalContext`；默认上限 `additionalContextLimit` **2500 token**（超出走"spilling"：全文存临时文件、模型收首尾预览+路径——大交接 MD 反而因祸得福，不截断）。
4. **headless `codex exec` 也触发 hooks**（官方："hooks 实现在 core agent loop，exec/TUI 无差异"），resume 路径也覆盖。
5. **⚠ 部署大坑：hook 信任机制**。非托管 hook 必须先在 TUI 里 `/hooks` 审查信任（按定义哈希记录），**未信任的 hook 被静默跳过且 fail-open**——headless/自动化场景尤其致命（0.121-0.147 期间有真实 bug：exec 完全不派发未信任 hook，PR #26434 已修）。落地时：先在 TUI 交互信任一次，或 CI 用 `--dangerously-bypass-hook-trust`。
6. **超时默认 600s、超时=不阻断**（比 CC 的 30s 宽松，但要显式设短）；SessionEnd/Interrupt 默认仅 1s。
7. Windows：`commandWindows`/`command_windows` 提供命令覆盖；命令在会话 cwd 下运行；Windows 上由哪个 shell 解释官方未说明（实现时要测）。
8. hook 触发时新 prompt **尚未写入** rollout（源码定论：先跑 hook、未阻断才落盘）——与 CC 的异步延迟殊途同归：闲置判断靠守望者外部记账，别解析会话文件。

### 6.5.3 DeepSeek Harness（dsh）侧核实结果（2026-09-16）✅ 存在、原生支持、还自带桥

1. **产品确认**：DeepSeek 官方 coding agent 就叫 **DeepSeek Harness**（`dsh`），2026-08-13 开源 developer preview（MIT，仓库 deepseek-ai/deepseek-harness，产品页 deepseek.com/harness），"everything is a plugin" 架构，默认模型 deepseek-flash（V4.1-Flash）。注意：npm/GitHub 上大量 `deepseek-harness-cli`/`deepseek-cli` 是社区仿品，官方只有 `@deepseek-ai/dsh`。
2. **原生拦截点（typed，比 CC/Codex 更正规）**：`agent/pre-step` 返回 `{kind:'reject'}` 即提交前拦截；`tools/pre-execute` 返回 deny/ask 做工具门禁；`agent/session-start` 注入上下文（不能阻断）。
3. **自带兼容桥**：官方内置 `dsh-hooks-claude-code` 插件直接跑现有 CC hooks.json——**UserPromptSubmit 的 deny 会正确转成 reject 阻断**（部分 CC 事件不支持，但本方案核心链路在支持列表内）；另有 `dsh-hooks-codex` 桥。⇒ 我们给 CC 写的钩子理论上在 dsh 上能直接复用。
4. **会话文件**：`~/.dsh/sessions/<规范化cwd>/<会话id>/session.jsonl.zstd`（**zstd 压缩**，守望者要会解压；可配 `compression:'none'`）；环境变量 `DSH_SESSION_JSONL` 直达当前会话文件。
5. 顺带（DeepSeek API 缓存）：自动开启、best-effort、TTL"几小时到几天"（官方不保证）；deepseek-flash 命中价低到 $0.003-0.006/M——DeepSeek 路线的缓存焦虑天然最小。

### 6.5.4 Pi / omp 及其他 CLI 横向核实（2026-09-16）

来源：pi-mono 官方 extensions 文档（packages/coding-agent/docs/extensions.md）、can1357/oh-my-pi docs/hooks.md、各家官方 repo/docs

| 工具 | 提交前拦截点 | 能否硬阻断 | 会话文件 |
|---|---|---|---|
| **Pi** | extension `input` 事件（提交点，skill展开前） | **能**：`{action:"handled"}` 完全跳过 agent loop（LLM 请求不发）；另有 `transform` 改写、`before_agent_start`/`context` 注入 | `~/.pi/agent/sessions/` 按目录分桶 JSONL（树结构） |
| **omp** | 同 Pi（hooks=extensions 包装，加 `.omp/hooks/pre|post` 目录约定） | 能（继承上游 `input`；`tool_call` 可 block） | `~/.omp/agent/`（sessions 精确路径待核实） |
| Gemini CLI | `BeforeAgent`（提交后规划前）+ `BeforeModel`（请求前） | 能（`decision:"deny"` / exit 2 → Block Turn） | `~/.gemini/` |
| Droid (Factory) | `UserPromptSubmit`（CC 同款） | 能（exit 2 / `decision:block`） | `.factory/`（未核实） |
| OpenCode | v1 `chat.message` / v2 `session.hook("prompt")` | 半能（无正式 deny API，靠抛异常中断 admission） | `~/.local/share/opencode/` 新版 SQLite |
| Crush | 无（UserPromptSubmit 未实现，只有 PreToolUse） | 否 | `%LOCALAPPDATA%\crush` 每项目 SQLite |
| Goose | `UserPromptSubmit` 存在但**仅观察**（官方："a block decision from those events is ignored"） | 否 | `~/.config/goose/` |
| Aider | 无 hooks（#2045 feature request 未实现） | 否 | `.aider.chat.history.md`（Markdown） |

**用户点名的四家（CC/Codex/Pi/DeepSeek Harness）全部具备提交前硬阻断**，且被拦请求都是 0 token、不落盘。Pi 的 `input.handled` 甚至是所有工具里最干净的提交点硬闸。

### 6.5.5 无钩子工具的兜底：代理层拦截（可行但启发式）

- **LiteLLM** 有官方一等能力 `async_pre_call_hook`：能读/改完整请求体，也能直接拒绝请求（返回自定义文案）——现成能力，无人做过"闲置超时"用途。
- **命门**：Anthropic 兼容协议里**没有 session id**，代理只能靠启发式近似"闲置"：input token 规模 + messages 条数判"大上下文恢复"（可靠）；用 (API key + messages 前缀哈希) 做状态表记"上次请求时间"（可做但脆弱，compaction/分支会打断哈希）；`cache_read_input_tokens` 是事后信号。
- **定位**：兜底层，覆盖 Crush/Goose/Aider 等无闸门工具（前提是它们都走同一个本地网关）；精度和体验不如原生钩子，不作为主路径。CC Switch 若要承担此角色需自研插件（其本身无请求级 hook；one-api 也无）。

### 6.5.6 拦截层总结论（三路核实完毕，无疑问遗留）

**可行。** 落地形态 = "一个本地守护进程 + 每个 Agent 一个瘦适配器"：

```
                    ┌─ CC:       UserPromptSubmit (exit2/JSON block, timeout 2-3s)
用户提交 prompt ──→ ├─ Codex:    UserPromptSubmit (decision:block, 需先信任hook)
                    ├─ Pi/omp:   input 事件 (action:"handled")
                    ├─ dsh:      agent/pre-step (reject) 或 CC hooks 桥
                    └─ (其他)    代理层启发式兜底（后期可选）
                              ↓ 全部问询同一个
                    本地守望者守护进程 (HTTP)：这个 session_id 闲置多久？有交接MD吗？
```

四家拦截语义对照：阻断时用户看到提示文案、prompt 不进上下文、不产生 token 消耗；各家小差异（Codex reason 必填+信任机制、CC 超时 fail-open、Pi 是 JS 扩展非 shell 钩子、dsh 需装桥或写插件）都已核实并记录在上文。守望者的"闲置判定"统一由守护进程自己记账（按 session_id 记最后活动时间），钩子侧不解析会话文件。

已知实现细节坑（提前记下）：钩子在"用户提交瞬间"触发，判断"真实闲置间隔"要排除刚输入的这条（看 transcript 倒数第二条的时间戳，需实测 hook 触发时新 prompt 是否已写入）。



| 路线 | 什么都不做（冷恢复第一轮） | 先总结成 MD 再开新会话 |
|---|---|---|
| Anthropic API（Opus 4.8） | 全量重读 $0.50 + 写缓存 $0.625 ≈ **$1.13** | 总结(Flash 类便宜模型)≈分钱级 + 新会话按 3-5K token 计 ≈ **<$0.05** |
| OpenAI API（gpt-5.3-codex） | 全量重读 $0.175 + 无写费 ≈ **$0.175** | 同上 ≈ **<$0.02** |
| GLM Coding Plan / ChatGPT 订阅 | 额度按全量 input 消耗（+慢） | 额度只消耗小上下文，速度快 |
| 本地 4090 Qwen3.8-27B 总结 | — | **0 元**（电费除外） |

注：数值为量级示意；订阅制的"额度折算"以各家 rate card 为准（Codex 已确认 cached input 按 10% 计额度）。

## 8. 风险与坑

1. **jsonl 格式无官方保证**（CC 官方明说 internal、版本间会变）——解析器必须防御式，字段没了退回 mtime-only。
2. **CC 2.1.232 < 2.1.242**：`promptCacheTtl` 等新配置不可用；升级 CC 是独立决策（OMC 体系对 CC 版本有兼容要求，需先确认）。
3. **CC Switch 转发 `anthropic-beta` 头与否**影响 1h TTL 能否经代理生效（若走这条路需实测）。
4. **20MB 级会话文件**：总结器输入要做截断策略（只取消息文本、跳过/截断大工具输出），否则便宜模型也吃不下一整只 20MB。
5. **会话"活着"误判**：CC 后台任务（长命令、subagent）会持续写文件——闲置判定要看"最后写入"而非"用户最后输入"（保守起见按最后写入时间算，宁可多等）。
6. **30 天自动清理**（`cleanupPeriodDays` 默认 30）：交接 MD 库要独立于 transcript 存活——这正是"总结外置"的另一个好处：transcript 被清了，交接还在。
7. 多机器（NUC10/服务器）上的会话不在此工具视野内——本工具先只管本机。

## 9. 决策记录（2026-09-16 用户拍板）

| # | 事项 | 决定 |
|---|---|---|
| 1 | 总结模型 | 留空=可配置项，后续再议（候选：GLM-5.3-Flash / 本地4090 Qwen27B / 主力模型） |
| 2 | 闲置阈值 | 默认 **30 分钟**，用户可调；按 API/服务商/模型分别设（各家缓存 TTL 不同：Anthropic 5m/1h、OpenAI 30m、GLM 实测 ≤10 分钟必活/≥30 分钟必死，2026-09-17） |
| 3 | 最小上下文门槛 | 留默认值+可配置 |
| 4 | 界面 | **先不做**；先做核心后端功能的验证（跑通"监控→总结→拦截→续接"闭环），确认可行可用后再推进 UI |
| 5 | Claude Code 升级 | **不升级**（2.1.232 保持；拦截方案用不到 2.1.242+ 的新功能；用户听闻新版本出过问题） |
| 6 | 项目启动 | **暂不立项**，继续调研讨论直到无疑问 |

### 尚待讨论的小决策（不阻塞后端验证）
- 拦截策略：超时但**还没有**交接 MD 时，放行+警告 or 也阻断？（默认建议：放行+警告）
- 阻断的 prompt 会被抹除，用户 /clear 后需重打那句话（TUI 历史记录能否上翻找回，实测确认）
- 守护进程不可达时的默认行为：跟随各家原生 fail-open（CC/Codex 超时=放行），还是要做 fail-closed
- 总结触发阈值与拦截阈值是两个独立参数（如：闲置 30 分钟拦截问询；闲置 2 小时才自动总结）——是否分开配置
