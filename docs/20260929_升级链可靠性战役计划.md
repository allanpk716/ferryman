# 升级链可靠性战役计划（2026-09-29 拷问定案；同日端口 7311→15700）

> 2026-09-29 午后拷问会话产物，自包含。决策依据：`docs/adr/0018-quiet-gate-over-edge-proxy.md`、CONTEXT.md「升级窗口语义」节。

## 这套系统的几个词（先说人话，后文直接用）

| 词 | 人话 |
|---|---|
| 渡口 | 本机代理。Claude Code 的所有 API 请求先发给它（127.0.0.1:15722），它改写后转给智谱等上游 |
| 摆渡 | 把闲置会话的上下文要点整理成一份交接文档，供新会话接手 |
| 排水 | 停机前等正在跑的请求自然结束，不掐断（上限 180 秒） |
| 换装 | 替换程序文件：旧 exe 改名挪窝（叫"让位"），新 exe 顶上原名。Windows 下运行中的程序文件改得了名、覆盖不了，所以只能这么换 |
| 监督者 | 执行升级事务的那段程序，就是 `ferryman update` |
| 蜂群 | 每个 CC 会话自带的"守护在不在？不在就拉起"钩子。一群会话各带一套，所以叫蜂群 |
| 看门 | 每 5 分钟探一次守护、不在就拉起的 Windows 计划任务 |
| 静默门 | 升级/重启动手前先等流量空闲（没有在途请求、近期没新请求）才动手的检查 |
| 自举属性 | 跑升级的程序永远是旧 exe——新代码还没落盘。所以任何升级逻辑的修复，都要等下一次升级才第一次真正执行 |

## 证据底座（为什么打这役）

1. **09-29 上午两次自动升级全失败**（update.log 实锤）：10:25 升 v0.2.5、10:40 升 v0.2.6，剧本相同——停旧 36 秒（旧监督者只软等 30 秒、旧进程没退就硬走）→ 换装成功 → 90 秒版本校验全静默 → 回滚。每次约 2 分钟全场停顿，v0.2.6 最终 10:54 手工换装上线。
2. **监督者永远是旧 exe 的代码**（见上表"自举属性"）：v0.2.6 里的硬门修复（等旧进程真正退场才换装，预算 240 秒）至今零次真实执行。
3. **拉起不可验证**：监督者拉新守护要经过 wscript→VBS→cmd→exe 三级转手，出错信息被吞、成败没人检查（07:31 事故第一根因同款；10:41 那次 90 秒里 serve 日志零启动痕迹，拉起本身可疑）。
4. **蜂群抢跑**（问题清单 P5）：停旧后的子秒窗口内，蜂群钩子会抢着拉起，版本校验可失败→自动回滚；监督者"复停重拉"兜不住蜂群在复停与重拉之间再抢。
5. **本质缺口**：就算全对，排水窗（最长 180 秒）内**新发起的请求会被拒连**——空载升级全程 4 秒没感觉，白天有长流在跑时最坏约 3 分钟。

## 定案（12 问全收，详见 ADR-0018）

- 病分两层：先治可靠性（本役），停顿病用**静默门**逼近（空载 4 秒），"任何时刻都不拒连"的常驻代理架构**延后**（ADR-0018 附录存了设计草图，将来要做不用重新想）。
- "无缝升级"＝在途流不断＋新请求不拒连，**延后目标**；本役验收线＝在途流零截断＋单次拒连窗 ≤10 秒。
- 升级瞬间内存状态（快照、判热时钟、等待窗）冷启重建、不做交接（现状语义写死；观察周 104 次警告零漏拦证明重启后冷态不伤正确性）。
- 范围排除：守护无痕死亡（P1）、闸门 enforce 拍板（P2）、心跳零发跳（P4）**不进本役**。

## 工作项（载具 v0.3.0）

### W1 静默门
- 守护侧：/stats 暴露 `dock_inflight`（渡口在途请求数）与 `last_request_ts`（最后一个请求时刻）。
- 监督者侧：动手前查旧守护，判据＝**在途=0 且距最后请求 ≥10 秒**。不满足默认等 60 秒；终端在场则交互问（继续等/现在切/放弃），非交互发 notify 告警后硬切（兜底路径）。旗标 `--wait-quiet=<dur>` / `--force` 供脚本态。**硬切不适用验收线（D10）**：其拒连窗（最长约排水上限 180s）与可能的截断如实记录进 update.log，事后可查。
- restart-daemon.ps1 查同一端点、同门逻辑。
- 自举注意：门查的是旧守护，载具自己那次升级没有门（照旧空载手动换装）。

### W2 拉起修复（ADR-0015 第 2 条部分修订，见其补记）
- 监督者事务拉起弃 wscript/VBS 层，走 `cmd.exe /c start-daemon.cmd + CREATE_NO_WINDOW`（不闪窗的正确旗标；启动知识仍单源于点火脚本）。
- 加**拉起验证**：spawn 后 2 秒起做活性探针（进程活或 15700 应答；重试至 10 秒截止，覆盖冷启实测 3s 的余量）。探针失败只报相位错误＋notify 告警，**不单独触发回滚**——回滚仍由既有 90 秒版本校验裁决。
- 蜂群/看门/Run 键的 VBS 链**不动**（它们靠冗余自愈，不挂事务）。

### W3 蜂群抢跑修复＋锁盲区修
- 守护层拦（一处实现盖住所有拉起方）：serve 启动早期查 update.lock——持有者活（PID 活且映像属于 {换装目标, 自中继副本}）→ 打印一行、退出码 0 静默让路。锁判定逻辑从 update 包导出只读助手，不复制第二份。
- 自举干净：修复随**升级目标**走，第一次升到载具版本即生效。
- 顺手修既有缺陷：`lock.go` 持有者判定对自中继副本（监督者的临时副本 exe）永远判陈旧 → 并发第二次 update 会误接管、双监督者齐跑。判定集合加入副本路径。
- 监督者"复停重拉"保留为最后防线。

### W4 彩排台（可复用资产，非一次性脚本）
- 影子实例：独立数据目录/独立双端口/独立启动脚本/本地桩发布端点；真构建两版 exe 跑完整升级事务，探针流全程打。
- 注入故障集：拉起即杀、模拟蜂群抢拉旧版、陈旧锁、备份位被占、排水中强断。
- 验收（三场景；验收线按 D10 只适用于静默门达成的升级）：
  - **静默路径**（间歇流量，间隙 ≥10s）：门放行；连续 10 次事务零截断、拒连窗 ≤10s
  - **强制路径**（`--force`＋1 rps 探针全程打）：测拒连窗与窗内行为，如实记录，不判 ≤10s
  - **长流场景**（在途流 >60s）：零截断（排水窗内自然跑完）＋硬切边界的截断行为如实记录
  - 注入故障集逐项按设计恢复（三场景通用）。

### W5 杂活（未决——对外 GitHub 动作，待用户批准后执行，不进 v0.3.0 实施包）
