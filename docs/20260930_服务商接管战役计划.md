# 服务商接管战役计划（2026-09-30 定案；目标＝卸载 cc-switch）

> 自包含。证据全部来自 2026-09-30 对生产链路的实测解剖（cc-switch 数据库/源码/配置三面交叉）。术语速查见 `docs/20260929_升级链可靠性战役计划.md`；渡口＝本机代理 15722。

## 几个词（先说人话）

| 词 | 人话 |
|---|---|
| 供应商 | 一家模型 API（智谱 GLM、Kimi、AiHubMix…），有自己的地址、密钥、协议口音 |
| cc-switch | 你现在用的供应商切换器：开着本地代理（15721），两边编辑器的配置都指向它，它按"当前供应商"转发，并替 codex 做协议翻译 |
| 协议翻译 | codex 说 OpenAI 的 responses 方言，智谱只听 Anthropic 的 messages 方言——中间要有人逐句转述（请求、流式事件、工具调用、用量都要转） |
| 接管 | Ferryman 自己管供应商：渡口当总门（CC、codex 都进它），切换=改渡口上游表，编辑器配置一次写死指向渡口、再也不动 |

## 证据底座（为什么打这役）

1. **cc-switch 今早把 CC 的流量偷走了**：它随开机自启＋"会话自动同步"在 CC 启动时把 `~/.claude/settings.json` 改回自己的 15721，当前供应商又直连智谱——渡口从 08:25 起被旁路（快照/同模型摆渡前缀/心跳/静默门判据全瞎），11:38 手术后才恢复。
2. **智谱不认 codex 的方言**（实测 404 + cc-switch 源码双证实）：直连 `bigmodel/api/coding/paas/v4/responses` 必败；cc-switch 的价值残骸只剩代理里的 responses↔Anthropic 翻译（forwarder.rs 3210 行起）。
3. **orca 的 codex 先天坏**：orca 给 codex 设了独立的家（`CODEX_HOME=%APPDATA%\orca\codex-runtime-home\home`），那份配置直连智谱＋responses＝必 404（九月零调用未踩到）。
4. **cc-switch 写配置是整文件重写**，会抹掉别人的行（`[features] hooks = true` 每次开机必丢）。
5. **今天的外科手术（interim）**：CC 已直连渡口 15722（端到端验证）；codex 暂留 cc-switch 代理（验证可通）；其"会话自动同步"已关、自启保留（codex 还需要）。备份 `*.bak-ferryman-20260930` 在位。

## 定案（2026-09-30 用户拍板）

- **D1 范围**：只接管 CC＋codex（gemini/opencode/pi 等不学 cc-switch 全家桶）。
- **D2 codex 车道**：**并入渡口**——渡口加一条翻译车道，不再有独立翻译进程。
- **D3 操作面**：CLI 先行（`ferryman provider` 命令族），面板页后补。
- **D4 节奏**：今日定计划，实施走夜链。

## 目标拓扑（接管完成后）

```
CC ────────┐
           ├─→ 渡口 15722 ──┬─→ 上游表当前供应商（Anthropic 方言：改写+鉴权注入，现状能力）
codex ─────┘        │        └─ 翻译车道（responses↔Anthropic，本役新增）
                    └ 切换供应商 = 只改渡口上游表；编辑器配置永远指向 15722，一次写死不再动
```

关键设计：**切换零写盘**。两家编辑器的配置只在接管时写一次（指向渡口）；此后切供应商只翻渡口的上游表——配置文件再也不会被谁改来改去（今早那种"开机被偷"事故从结构上消灭）。切换对**在跑会话即时生效**（不用重开会话，比 cc-switch 的改文件模式强）。

## 工作项（载具 v0.4.0）

### W1 渡口 codex 翻译车道（核心、最难）

- **W1a 对照表先行**：通读 cc-switch 源码翻译层（`src-tauri/src/proxy/forwarder.rs` 及 converter 族；仓库规矩：中转怪癖禁止臆造，必读参考实现），产出两方言的完整对照表：请求体、SSE 事件流（含 tool_use 流、thinking 流、usage 事件、错误事件）、鉴权头、端点变体（`/responses` 及变体路径）。对照表是本票的规格，评审先审表后审码。
- **W1b 车道实现**：渡口按路径分流（`/responses*` → 翻译车道；`/v1/messages` → 既有车道），翻译后走既有上游改写/鉴权注入；GLM 生成须 `thinking:disabled`（ADR-0015 既有纪律）在翻译层落实。快照/摆渡对 codex 车道**首版不进**（只记账：dock 事件+账本四列），观察后再说。
- **W1c 回放测试**：真 codex 流量录制成夹具（正常回复/工具调用/长流/错误注入四形），翻译车道全量回放比对；挂进既有测试体系。

### W2 配置写入器（一次性接管＋修复）

- CC：外科式改 `~/.claude/settings.json` 的 env 块（`ANTHROPIC_BASE_URL`→15722），**其余一字不动**（hooks/plugins/别人的键都不碰——cc-switch 整文件重写是反面教材）。
- codex 两份：`~/.codex/config.toml` 与 orca 的 `CODEX_HOME` 那份——`base_url`→渡口、保持 `wire_api="responses"`（渡口车道就说这个方言）、删 `PROXY_MANAGED` 占位、`[features] hooks=true` 保住；顺手修好 orca 那份先天坏账。
- 幂等：重跑=校验+补缺，不做整文件重写。doctor 加三项体检（CC 指向、codex 指向、orca codex 健康）。

### W3 `ferryman provider` 命令族

- `list / switch <名> / add / remove / import-ccswitch / apply`。
- 上游表扩列：每供应商带"codex 可用性"（原生 responses / 需翻译 / 不支持）＋模型位映射（CC 三档位＋codex 主模型）。
- `switch`＝改渡口上游表＋即时生效；`apply`＝跑 W2 写入器（接管时用一次，此后只在体检报修时用）。
- `import-ccswitch`：一次性从 `~/.cc-switch/cc-switch.db` 导入现有供应商（含密钥，本机落 config，T39 隐私纪律，不入 git）。

### W4 迁移与验收

1. 彩排/回放：W1c 夹具全绿。
2. 生产实证：接管后 **CC 与 codex（含 orca 生态）各跑一天真实工作**零人工修复；切换供应商一次即时生效且在跑会话不断流。
3. **cc-switch 退出**：托盘退出→自启关→卸载；重启电脑一次，三件全绿（CC 走渡口、codex 走渡口、`hooks=true` 在位）——这一条同时就是"cc-switch 事故绝缘"的终验。

### W5 杂活

- 卸载 cc-switch（用户手工，App 卸载器）；`~/.cc-switch/` 目录留档一月再清（数据库里有密钥，清理即销毁）。
- 文档：本计划收官记录；CONTEXT.md 增补"供应商"词条；记忆更新。
