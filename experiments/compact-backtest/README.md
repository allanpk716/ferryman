# CC /compact 节律回测（compact rhythm backtest）

用用户自己的 50 天账本（`~/ferryman/accounts/*.jsonl`，usage 流水）对更朴素的"CC `/compact` 节律"做预演：先从账本识别真实 compact 事件、标定 compact 后前缀 Y，再对每个会话重放请求序列，比较"实际发生"与"前缀超过阈值 P 就 compact 一次"两种世界的输入侧花费。动机与上位结论见 `experiments/cost-structure/`（82% 花费在 cache_read）与 `docs/research/20260918_billion-context持续压缩调研.md`（代理级持续压缩理论净省 20-35%）；本脚本回答的是：**用 CC 手动 /compact 节律，在这份账本上能省多少**。

## 用法

```bash
python experiments/compact-backtest/compact_backtest.py                 # 默认 ~/ferryman/accounts + GLM 价 + 默认网格
python experiments/compact-backtest/compact_backtest.py --prices 6.9 1.7 24 10000
python experiments/compact-backtest/compact_backtest.py --grid "150k,300k|63k"   # 自定 P/Y 网格（k 后缀可用）
python experiments/compact-backtest/compact_backtest.py --compact-cr-max 30000   # 收紧 compact 识别（cr 上限）
```

- `--data`：账本目录（默认 `~/ferryman/accounts`）。
- `--prices P_in P_cache P_out per`：积分/万 token（默认 GLM v2026-09-17：6.9 / 1.7 / 24 / 10000）。
- `--grid "P列表|Y列表"`：回测网格，token 支持 k 后缀（默认 `100000,150000,200000,300000|63000,20000`，63k=实测 Y p50）。
- `--compact-cr-max`：compact 识别的 cache_read 上限（默认 45000，理由见下）。
- `--top N`：代表会话展示前 N 个（默认 2，按 cache_read 降序）。

只读账本，不写任何文件。输出 UTF-8。分组键用 `lineage_id`（= 会话转录文件路径；本账本中 lineage 与 session_id 逐一对应，取更稳的路径）。

## 判定规则（步骤 1）

按 lineage 分组、按 ts 排序，前缀 P = input + cache_read + creation，跳过零 token 行：

- **compact 事件**：旧 P ≥ 80k 且 cr < 45k 且 新 P ≤ 50% 旧 P 且 新 P ≤ 100k。
  cr 上限取 45k 的依据：对全部满足其余条件的暴跌事件做 cr 直方图，45k 以上为空；30~45k 一档（cr≈34-36k）是 compact 后"系统+工具"前缀仍在 TTL 内的内容寻址命中，同为 compact。收紧到 30k 只剩 12 次，结论方向不变。
- **闲置复活**（仿真中照真实计费）：input ≥ 80% 旧 P 且 cr < 10k 且 与前请求间隔 ≥ 30min。
- 另有一簇 ratio 0.5~0.7、新前缀 88~144k 的中幅下跌（约 10 次）未计入：签名介于 compact 与"带上下文续接"之间，无法从 usage 流水判别，计入只会增加事件数、对 Y p50 影响不大。

## 基准读数（2026-09-18，2026-07-30~09-18，66,503 行 / 250 会话）

与 `ledger_cost_structure.py` 同口径（台账行即计费行），总花费 3,033,417 积分，其中输入侧 2,849,590（94%）、output 常量 183,827（6%）。

| 项 | 读数 |
|---|---|
| 真实 compact 事件 | **53 次**（旧 P p50 ≈ 430k，跌至 45~87k，ratio 0.09~0.48；间隔 p50 17 分钟，34/53 发生在活跃工作中） |
| compact 后前缀 **Y** | **p50 63k · p90 78k** · min 45k · max 87k（= 系统+工具 ~35k + 摘要 + 首条消息） |
| 闲置复活 | 126 次（对照：cost-structure 全款重付 723 次是更宽口径） |

### 节律仿真网格（输入侧口径；"对总花费"已除以含 output 的总额）

| P→Y | 策略输入侧 | 省积分 | 对输入侧 | 对总花费 | compact 总次数（会话级 p50/p90/max） |
|---|---:|---:|---:|---:|---|
| 100k→63k | 1,659,106 | 1,190,484 | 41.8% | 39.2% | 6,222（18/83/276） |
| 100k→20k | 1,169,129 | **1,680,461** | **59.0%** | **55.4%** | 3,734（10/55/174） |
| 150k→63k | 1,764,210 | 1,085,380 | 38.1% | 35.8% | 3,448（11/54/166） |
| 150k→20k | 1,393,558 | 1,456,032 | 51.1% | 48.0% | 2,702（8/44/132） |
| 200k→63k | 1,957,322 | 892,267 | 31.3% | 29.4% | 2,555（10/43/128） |
| 200k→20k | 1,617,533 | 1,232,057 | 43.2% | 40.6% | 2,156（8/36/111） |
| 300k→63k | 2,376,271 | 473,318 | 16.6% | 15.6% | 1,738（7/30/94） |
| 300k→20k | 2,091,502 | 758,087 | 26.6% | 25.0% | 1,548（6/27/86） |

**敏感性**：P 从 100k 放到 300k（Y=63k）省积分摆动 717,165；Y 从 63k 压到 20k（P=150k）摆动 370,652。**P 是更敏感的参数**——阈值决定"多久付一次 430k 级前缀的全额读"，Y 只决定每次重进的小头。

**代表会话**（最优档 100k→20k，脚本第 [4] 段有逐段 ASCII 对照）：
- `…93ce2cb98b2d`「推进 writing-plans」2301 行：输入侧 149,408 → 48,363（省 68%，compact 145 次）。
- `…c315ac8525f5`「Clarify which questions…」2502 行：144,583 → 47,621（省 67%，compact 160 次）。

对照实测：用户 50 天只 compact 了 53 次（≈1 次/天，旧 P 中位 430k）；仿真在 P=300k 档也要 1,738 次（≈35 次/天）才拿到 15.6% 总节省——**手动节律要吃到两位数节省，频率得提高一个数量级**。

## 假设与限制（结果为上界）

1. **零质量税**：仿真假设 compact 后模型质量与决策不变。这是最强的假设——压缩掉的历史会以质量损失的形式回来，现实节省要打折。对照：代理级持续压缩（billion-context 调研）净省 20-35%，本回测的 39-55%（对总花费）是"无质量损失上界"。
2. **Y 恒定**：每次 compact 后前缀都取同一 Y（63k 或 20k）。实测 Y 本身在 45-87k 间波动。
3. **压缩调用同价目**：compact 调用按 旧前缀×cache 价 + 3000 token 摘要×output 价 计。
4. **复活照真实计费（保守）**：闲置复活的全额重付按账本原样保留——实际上 compact 后前缀变小，复活重付也会变小，此处未给策略记这笔便宜。
5. **台账行口径**：账本存在秒级连排的同用量行（offset 为书签字段、非逐消息唯一），基线与策略对同一行序列计费，百分比口径一致；绝对积分与 `ledger_cost_structure.py` 完全对齐。
6. 真实发生的 53 次 compact 在仿真中不特殊处理（由阈值逻辑自然触发）；实测 Y 的 p50/p90 直接取自这 53 次事件的跌后前缀。
